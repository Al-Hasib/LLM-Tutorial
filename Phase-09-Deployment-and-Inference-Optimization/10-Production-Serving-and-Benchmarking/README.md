# Production Serving and Benchmarking

**Phase:** [Deployment and Inference Optimization](../README.md) · **Topic folder:** `10-Production-Serving-and-Benchmarking`

## Why this matters

[Lesson 4](../04-Serving-Frameworks/README.md) covered how *one* serving process — vLLM, TGI, SGLang, whatever — manages KV-cache memory and batches requests efficiently on a single fleet of GPUs. That is necessary but nowhere near sufficient for an actual production system: a single process, however well it batches, has no protection against a traffic burst that exceeds its capacity, no way to spread load across the many replicas of that process a real deployment needs, no way to grow or shrink the number of those replicas as demand rises and falls over a day, and no built-in way for anyone operating it to know whether it's actually healthy. This lesson is the layer wrapped *around* the serving process from Lesson 4 that turns it into a system serving real, unpredictable, multi-tenant traffic reliably: bounded queues and admission control in front of it, load balancing across many replicas of it, autoscaling the number of those replicas, and the observability metrics needed to tell whether any of this machinery is working at all. Along the way it also completes the standard metric vocabulary this whole phase has been building: [Lesson 3 §7](../03-KV-Cache-and-Speculative-Decoding/README.md#7-ttft-and-itl-the-two-per-request-latency-metrics) already introduced TTFT and ITL, the two per-request latency numbers prefill and decode each produce; this lesson adds TPOT, throughput, concurrency, and GPU utilization to that vocabulary — precisely the metrics [Lesson 6](../06-Cost-and-Latency-Optimization/README.md)'s cost/latency trade-offs are measured *in*.

## What this lesson covers

- What a bare inference process is missing to become a production system

## 1. From a model process to a production system

Everything in [Lesson 4](../04-Serving-Frameworks/README.md) happens *inside* one serving process: it accepts requests, pages KV-cache memory efficiently, and batches (continuously, with chunked prefill) whatever is currently in flight. Point real, internet-scale traffic at that process alone, though, and four gaps show up immediately:

- **No protection against overload.** If requests arrive faster than the process can serve them, what happens? Nothing in Lesson 4's scheduling logic answers this — it assumes requests are already queued and ready to be admitted, not that the queue itself might need bounds.
- **No way to spread load across GPUs.** One process, however well it batches, tops out at the throughput of the GPU(s) it owns. Real capacity comes from *many* replicas of that process running on many GPUs, and something has to decide which replica each incoming request goes to.
- **No way to grow or shrink capacity.** A fixed number of replicas is either wasteful (over-provisioned for the traffic trough) or overloaded (under-provisioned for the traffic peak) — real traffic is never flat.
- **No way to know if it's healthy.** None of the above can be managed without numbers: is the queue backing up, is latency creeping past what users tolerate, is the GPU actually the bottleneck?

Sections 2 through 6 below answer each of these gaps in turn: bounded queues and admission control (§2) for overload, load balancing (§3) for spreading load across replicas, autoscaling (§4) for growing and shrinking capacity, observability (§5) for health, and multi-tenancy (§6) for the case where several of the above are all happening *at once* on shared capacity.

## 2. Request queues and admission control

Every serving process has a queue of requests waiting to be admitted into a batch. The single most important design decision about that queue is that it must be **bounded** — capped at some maximum depth — rather than allowed to grow without limit. An unbounded queue feels safe (nothing is ever rejected), but under sustained overload it does something worse than rejecting requests: it accepts all of them and makes *every* request, including requests that arrive early, wait behind an ever-growing backlog. Queueing latency for a request admitted deep into an unbounded queue can grow arbitrarily large — there is no ceiling on how long a user might wait, and by the time a response finally comes back it may be useless to whoever asked for it.

**Load shedding** is the fix: once the queue reaches its bound, new requests are rejected (or "fast-failed" — returned an error immediately) rather than accepted and left to wait. This sounds like a worse outcome than an unbounded queue — some requests get nothing at all — but it is a deliberate trade: shedding load caps the *worst-case* latency any accepted request experiences, at the cost of some requests being turned away outright during an overload instead of everyone being kept waiting indefinitely. A client that receives a fast rejection can retry against another replica, back off, or surface a clear error to its own user — all strictly better options than a response that silently arrives minutes late. `example.py` §1 simulates exactly this contrast: the same bursty arrival process fed once through an unbounded queue and once through a bounded queue with load shedding, with real measured queueing-latency percentiles in each case.

A bounded queue with a single admission rule still treats every request identically, which is itself often wrong: a production system usually serves more than one kind of traffic against the same capacity — interactive chat that a user is actively waiting on, and batch or background jobs (a nightly summarization run, an evaluation sweep) that nobody is watching in real time. **Priority queues** (or priority *classes*) fix this by giving each traffic class its own queue and its own admission/scheduling priority, so a burst of low-priority batch jobs can't fill up capacity and starve the high-priority interactive class's latency SLO — the batch class simply waits longer, or gets shed first, while the interactive class's requests are admitted ahead of it. This is the same idea §6 revisits at the multi-tenant level: isolating one workload's burst from degrading another's guarantees.

## 3. Load balancing across replicas

Once there is more than one replica of the serving process from Lesson 4, something in front of them has to decide, for each incoming request, which replica gets it. Three policies, in increasing order of sophistication:

- **Round-robin**: send request 1 to replica 1, request 2 to replica 2, and so on, cycling back around. Trivial to implement, and reasonable when every request costs about the same — but real LLM requests very much do not: a one-sentence answer and a multi-page response occupy a replica's capacity for wildly different amounts of time, and round-robin has no idea which replicas are currently loaded down with long-running requests and which are sitting nearly idle.
- **Least-outstanding-requests**: route each new request to whichever replica currently has the *fewest* in-flight requests. This adapts to uneven request costs automatically — a replica stuck serving several long generations naturally stops receiving new work until some of its slots free up, without the router needing to know anything about how long any individual request will take. `example.py` §2 measures this contrast directly: round-robin vs. least-outstanding-requests routing a stream of requests with randomly varying output lengths across a small fixed number of replicas, with the resulting per-replica load imbalance measured, not asserted.
- **KV-cache-aware / prefix-aware routing**: route a request to whichever replica *already has* its prompt prefix cached in memory from a previous request, avoiding a redundant prefill entirely on whichever replica it would otherwise have landed on. This is the fleet-scale generalization of two ideas this phase already covered at the scale of a single server: [Lesson 4 §6](../04-Serving-Frameworks/README.md#6-sglang-automatic-general-purpose-prefix-sharing)'s RadixAttention shares cached prefix blocks *within* one SGLang process's memory, and [Lesson 6 §2](../06-Cost-and-Latency-Optimization/README.md#2-prefix-caching-paying-for-a-shared-prompt-once)'s prefix caching amortizes a shared prompt's prefill cost *within* one server. Prefix-aware routing takes the identical idea and extends it across an *entire fleet*: the router itself tracks (approximately) which replicas hold which cached prefixes, and steers requests that share a prefix toward the replica that already paid for it, rather than treating every replica's cache as isolated and paying the prefill cost again wherever least-outstanding-requests happens to land.

None of these three policies is strictly better in every situation — round-robin is simplest and good enough when request costs really are roughly uniform; least-outstanding-requests is the standard choice for uneven LLM workloads; prefix-aware routing pays off specifically when a large fraction of traffic shares real prompt prefixes (long system prompts, shared retrieved documents), and costs some routing complexity to get right.

## 4. Autoscaling

A fixed number of replicas is a fixed capacity ceiling, sized for *some* traffic level — too many replicas during a quiet period wastes GPU spend, too few during a peak means the queues from §2 fill up and requests start being shed. **Autoscaling** adds and removes replicas automatically based on observed load rather than a hand-picked constant, driven by the same signals §5 defines precisely: queue depth (how backed up is the admission queue right now), p99 latency crossing an SLO threshold (are accepted requests starting to feel it), and GPU utilization (is existing capacity actually busy or sitting idle).

LLM serving has one autoscaling wrinkle that a typical stateless web service does not: **cold start is expensive**. Scaling up a stateless web replica usually means starting a lightweight process in seconds. Scaling up an LLM-serving replica means loading a model's weights — often tens of gigabytes — from disk or network storage into GPU memory before that replica can serve a single request, which can take substantially longer than a typical service's cold start. This has a direct consequence for *when* autoscaling has to react: because a new replica isn't actually useful until its (slow) cold start finishes, the autoscaler must react to rising load well *before* the queue actually overflows — scaling on a leading indicator like queue-depth trend or early latency creep, not on the queue already being full — or the new capacity will arrive too late to help the burst that triggered it.

## 5. Observability: the standard metric vocabulary

Everything in §2-4 is unmanageable without numbers to act on. This section defines, precisely, the standard metrics a production LLM-serving system reports — some already introduced, the rest completing the vocabulary.

**TTFT (Time to First Token)** and **ITL (Inter-Token Latency)** were already defined in [Lesson 3 §7](../03-KV-Cache-and-Speculative-Decoding/README.md#7-ttft-and-itl-the-two-per-request-latency-metrics): TTFT is the latency from request arrival to the first output token (dominated by prefill, plus queueing time), and ITL is the latency between each subsequent pair of output tokens (the cost of one decode step). This lesson adds:

- **TPOT (Time Per Output Token)**: the *average* per-token decode latency over an entire request, computed directly from a request's total latency:

  ```
  TPOT = (total_latency - TTFT) / (num_output_tokens - 1)
  ```

  TPOT and ITL measure the *same underlying per-step cost* — the memory-bandwidth-bound cost of one decode step — but at different granularities: ITL is reported per individual step (or as a distribution across steps), while TPOT is a single number averaged over an entire request's decode phase. Some literature and some serving frameworks use "TPOT" and "average ITL" interchangeably; this is not a mistake, it is the same quantity computed the same way, just under two different names. `example.py` §3 computes both directly from simulated per-token completion timestamps, so the relationship is visible in real numbers rather than left as a definitional footnote.

- **Throughput** (tokens/sec): at the *per-request* level, throughput is simply `num_output_tokens / total_latency` for that one request. What matters far more for capacity planning is *aggregate* (fleet-level) throughput: the sum of tokens/sec produced across every request being served concurrently right now, which is the number that actually answers "how much traffic can this deployment handle." A server can have mediocre per-request throughput (each individual request feels no faster than serving it alone) while still having excellent aggregate throughput, because it is serving many such requests at once — this is exactly the payoff of the batching Lesson 4 covers, measured as a number instead of asserted as a benefit.

- **Concurrency**: how many requests/sequences a server is serving at once — the live count of in-flight sequences that continuous batching ([Lesson 4 §4](../04-Serving-Frameworks/README.md#4-hugging-face-tgi-continuous-in-flight-batching)) is dynamically packing into its available slots at every scheduling tick. Concurrency is the input that produces aggregate throughput: more concurrent sequences generally means higher aggregate throughput, up to the point where the hardware's memory-bandwidth (or compute) ceiling is reached.

- **GPU utilization**: the fraction of time the GPU's compute units are actually busy executing work. This is the metric most often *misread*: a high utilization number sounds like "the GPU is the bottleneck, add more GPUs" or "everything is running efficiently," but [Lesson 1 §6](../01-GPU-and-Hardware-Fundamentals/README.md#6-the-payoff-why-prefill-is-compute-bound-and-decode-is-memory-bound) already established that decode is *memory-bandwidth*-bound, not compute-bound — a GPU can show high "utilization" (its compute units are technically issuing instructions, or the profiler's notion of "busy" counts time spent waiting on a memory-bound kernel) while the real bottleneck is bandwidth, not FLOPs. GPU utilization must always be read alongside the compute-bound/memory-bound distinction from Lesson 1, never as a standalone verdict on where the bottleneck actually is.

Together, TTFT/ITL/TPOT/throughput/concurrency/GPU-utilization are exactly the numbers [Lesson 6](../06-Cost-and-Latency-Optimization/README.md)'s batching and prefix-caching trade-offs are traded off *in* — that lesson describes the shape of the trade-off (bigger batches raise throughput and raise latency); this lesson's vocabulary is how that trade-off gets measured and reported on a real running system.

## 6. Multi-tenancy

Production capacity is rarely dedicated to a single workload — the same GPU fleet often serves multiple models, or multiple customers, or multiple internal teams' workloads, at once. This reintroduces, at the tenant level, exactly the problem §2's priority classes solved at the traffic-class level: the **noisy-neighbor problem**, where one tenant's traffic burst degrades latency for every *other* tenant sharing the same underlying capacity, even though that other tenant did nothing differently.

The usual mitigation is **per-tenant SLOs, rate limits, and quotas**: cap how much of the shared capacity (requests/sec, concurrent sequences, tokens/sec) any one tenant can consume, so a burst from tenant A is bounded before it can starve tenant B's latency guarantees — the same priority-queue idea from §2, just partitioned by tenant instead of by traffic class.

How isolated tenants actually are, though, is a genuine, unresolved trade-off rather than a solved problem. Some serving stacks isolate tenants at the process or GPU level entirely — tenant A's requests never share a batch, a KV cache, or even a GPU with tenant B's — which gives strong isolation (nothing tenant A does can ever slow down tenant B) at the cost of utilization (each tenant's dedicated capacity sits idle whenever that tenant's own traffic is low, exactly the static-allocation waste this whole lesson is trying to avoid). Others share a single continuous-batching process across tenants, packing everyone's requests into the same batches and the same GPU memory — much better utilization (nobody's idle capacity goes to waste), but materially harder isolation (one tenant's burst competes for the same batch slots and the same memory bandwidth as everyone else's, and the priority/quota machinery above only bounds the damage, it doesn't eliminate it). Real production systems pick a point on this spectrum deliberately, and different tenants or different pricing tiers within the same deployment often sit at different points on it simultaneously.

## 7. The request/response API surface

Everything in §1-6 lives *behind* an interface a client actually calls, and that interface's own design carries real cost and latency consequences of its own, not just a syntactic choice. Two decisions dominate:

- **Streaming vs. buffered responses.** An LLM produces its output one token at a time (this whole phase's decode loop), and a naive API that buffers the *entire* response before returning it forces the client to wait for the full generation — TTFT and total latency collapse into the same number from the client's point of view, no matter how good §5's underlying TTFT actually is. **Streaming** (returning each token, or small chunks of tokens, to the client as soon as decode produces them — typically over Server-Sent Events or a chunked HTTP response) is what makes TTFT a *visible*, user-facing number at all: a client rendering a streamed response can show the first token the moment it's ready, rather than staring at a blank screen for the entire request's total latency. This is why essentially every production LLM API supports streaming as a first-class mode, not an afterthought.
- **A shared request/response schema.** Early LLM-serving APIs each invented their own JSON shape for "prompt in, tokens out." In practice, the OpenAI Chat Completions API's request/response schema (a list of role-tagged messages in, a message plus token-usage accounting out, with a `stream` flag toggling the streaming mode described above) has become the de facto standard that most self-hosted serving frameworks — including vLLM, TGI, and SGLang from [Lesson 4](../04-Serving-Frameworks/README.md) — now implement an OpenAI-*compatible* endpoint for, purely so existing client tooling built against that schema works unmodified against a self-hosted model. This is a convention, not a technical requirement of any of §1-6's machinery, but it matters in practice: it's the reason "swap which model backs this endpoint" is usually a one-line config change rather than a client rewrite.

Neither decision changes anything about how requests are queued, balanced, scaled, or observed (§2-6 sit entirely underneath this interface) — but both directly shape what a *client* experiences, which is ultimately the point of every metric in §5.

## 8. Recap: how it all composes

Put together, §2-6 form one system: a bounded, priority-aware queue (§2) admits requests up to a capacity that autoscaling (§4) adjusts in response to load; a load balancer (§3) spreads admitted requests across whatever replicas currently exist, increasingly intelligently as prefix-aware routing is added; observability (§5) is the instrumentation that tells every other piece of this system, and the humans operating it, whether it's actually working; multi-tenancy (§6) is what happens when several traffic classes or several customers all depend on this same machinery at once, with isolation and utilization pulling in opposite directions; and §7's API surface is the interface a client actually experiences all of the above through. None of these pieces is optional in a real deployment — a queue without admission control just delays an outage, a fleet without load balancing wastes replicas, replicas without autoscaling waste money or drop requests, and any of the above without observability is unmanageable.

[Lesson 11 (Frontier Inference Systems)](../11-Frontier-Inference-Systems/README.md) picks up exactly where §3's load-balancing/routing ideas leave off and pushes them further: disaggregating the *prefill* and *decode* phases onto separate, differently-provisioned pools of hardware (since [Lesson 1 §6](../01-GPU-and-Hardware-Fundamentals/README.md#6-the-payoff-why-prefill-is-compute-bound-and-decode-is-memory-bound) already established they have opposite compute/memory profiles, so they don't have to share the same replicas at all), and cache-topology-aware routing across heterogeneous hardware generations — the same fleet-scale routing problem this lesson introduces, at a level of sophistication only frontier serving systems have needed to build so far.
