# Distributed Inference at Scale

**Phase:** [Deployment and Inference Optimization](../README.md) · **Topic folder:** `09-Distributed-Inference-at-Scale`

## Why this matters

Every lesson so far in this phase has implicitly assumed the whole model fits and runs on **one** GPU: [Lesson 2](../02-Quantization/README.md) shrinks the weights to fit better, [Lesson 3](../03-KV-Cache-and-Speculative-Decoding/README.md) shrinks the redundant work one GPU has to do, [Lesson 4](../04-Serving-Frameworks/README.md) schedules requests onto that one GPU efficiently — but nowhere so far has the model itself needed to *span* devices. That assumption breaks in two genuinely separate ways once models get large enough. First, the weights plus the KV cache simply don't **fit** in one GPU's HBM at all — [Lesson 1 §2](../01-GPU-and-Hardware-Fundamentals/README.md#2-the-memory-hierarchy-hbm-vs-sram)'s "tens of gigabytes" ceiling is a hard wall, not a soft inconvenience, for a model with hundreds of billions of parameters. Second, even if it *does* fit, one GPU's peak FLOPs and memory bandwidth can cap throughput or latency well below what a real deployment needs, regardless of memory headroom. [Phase 04 Lesson 3](../../Phase-04-Pretraining-LLMs/03-Distributed-Training-Basics/README.md) already introduced data, tensor, and pipeline parallelism — but for **training**. This lesson explicitly recaps those three ideas (it does not re-derive them) and shows how each behaves differently once the workload is **inference**, especially autoregressive decode's one-token-at-a-time sequential dependency, which breaks several training-time assumptions outright (large micro-batch counts hiding pipeline bubbles, for instance, simply aren't available inside a single request's decode). It then covers two further forms of parallelism training doesn't need in the same way: **expert parallelism** (routing tokens to experts scattered across devices, [Phase 03 Lesson 4](../../Phase-03-LLM-Architectures-and-Types/04-Mixture-of-Experts/README.md)'s territory) and **sequence/context parallelism** (splitting one very long input across GPUs during prefill).

## What this lesson covers

- The two independent reasons to distribute inference at all: doesn't fit vs. too slow, and why the fix depends on which one you actually have
- Tensor parallelism, recapped and reframed for inference: why its communication happens on *every* forward pass, not once per training step, and why that pins it to fast intra-node interconnects
- Pipeline parallelism, recapped and reframed for inference: the bubble formula, and why decode has no "extra micro-batches" to hide it with unless the server has enough concurrent requests in flight
- Data parallelism, recapped and reframed for inference: the simplest scaling lever, and what it does *not* fix
- Expert parallelism: MoE's all-to-all dispatch, and the specific way small decode batches leave expert-holding GPUs idle
- Sequence / context parallelism: sharding the sequence dimension itself across GPUs for very long prompts
- A recap table comparing all five parallelism strategies side by side

## 1. Two independent reasons to distribute inference

Before reaching for any of the machinery below, it's worth being precise about *why* a single GPU is not enough, because the two possible reasons call for different fixes entirely.

**Reason A: it doesn't fit.** A large model's parameters, plus the KV cache for however many concurrent sequences the server needs to hold ([Lesson 3 §3](../03-KV-Cache-and-Speculative-Decoding/README.md#3-the-kv-cache-pay-for-each-tokens-kv-exactly-once)), can simply exceed the tens of gigabytes of HBM available on one accelerator ([Lesson 1 §2](../01-GPU-and-Hardware-Fundamentals/README.md#2-the-memory-hierarchy-hbm-vs-sram)). No amount of scheduling cleverness fixes this — the bytes have to live somewhere, and if they don't fit on one device they must be split across several. This is a **memory-capacity** problem.

**Reason B: it's too slow.** Even a model that fits comfortably on one GPU can be too slow for the latency or throughput a deployment needs: a single GPU's peak FLOPs cap how fast prefill can run, and its memory bandwidth caps how fast decode can run ([Lesson 1 §6](../01-GPU-and-Hardware-Fundamentals/README.md#6-the-payoff-why-prefill-is-compute-bound-and-decode-is-memory-bound)). This is a **speed/throughput** problem, and it exists even when memory capacity is a non-issue.

The reason this distinction matters: the fixes are not interchangeable. Reason A is solved by splitting the *model* across devices — tensor parallelism (§2) or pipeline parallelism (§3) — so that each device only has to hold a fraction of the weights. Reason B, when memory already fits, is often better solved by simply replicating the whole model and serving more requests in parallel — data parallelism (§4) — which does nothing at all for memory capacity but directly multiplies throughput. Reaching for the wrong tool (e.g. tensor-parallelizing a model that already fits on one GPU, purely to get more throughput) adds communication overhead for no capacity benefit that a second full replica wouldn't have solved more simply. Real large-model deployments usually need both problems solved at once, which is exactly why §2-§6 combine.

## 2. Tensor parallelism (recap + inference framing)

[Phase 04 Lesson 3 §3](../../Phase-04-Pretraining-LLMs/03-Distributed-Training-Basics/README.md#3-tensor--model-parallelism-splitting-individual-layers) already covered the mechanism: split an individual weight matrix column-wise (or row-wise) across devices, so each device holds and computes with only a *fraction* of that layer's parameters. Applied inside a Transformer block, this typically means splitting the attention projections across head groups (each device owns a subset of attention heads) and splitting the FFN's intermediate dimension ([Phase 02 Lesson 5 §5](../../Phase-02-Transformer-Architecture-Deep-Dive/05-LayerNorm-Residuals-FFN/README.md#5-the-position-wise-feed-forward-network-ffn)) in half across two devices, with each device computing its own partial output:

```
device 0: partial_out_0 = X @ W_1        (W_1 = first half of the sharded weight matrix)
device 1: partial_out_1 = X @ W_2        (W_2 = second half)
combine:  full_out = all_reduce(partial_out_0, partial_out_1)   -- or an all-gather, depending on the split
```

The mechanism is identical to training. What changes for **inference** is *how often* that combine step has to happen, and how sensitive it is to being slow. In training, the model runs a forward and backward pass once per optimizer step, over a large batch — the all-reduce/all-gather cost is real but amortized over a lot of useful compute per occurrence. In inference, the sharded layer runs on **every single forward pass** — prefill, and then every one of the (potentially hundreds of) subsequent decode steps for a request — so this communication is not a rare, amortizable event, it is a recurring tax paid at every step of every request's generation. Because decode-step latency ([Lesson 3 §7](../03-KV-Cache-and-Speculative-Decoding/README.md#7-ttft-and-itl-the-two-per-request-latency-metrics)'s ITL) is the metric users directly feel, this communication has to be **low-latency**, not just high-bandwidth: NVLink-class interconnects within one physical node keep the added latency small enough to be worth it, but tensor parallelism *across* nodes (ordinary networking, an order of magnitude higher latency) is usually a bad trade for inference — a whole request's per-token latency now depends on a network round trip that training's amortized-per-step communication never had to survive at this frequency. This is the central reason tensor parallelism for inference is almost always scoped to fit *within* one server's GPUs, not spread across a cluster.

## 3. Pipeline parallelism (recap + inference framing)

[Phase 04 Lesson 3 §4](../../Phase-04-Pretraining-LLMs/03-Distributed-Training-Basics/README.md#4-pipeline-parallelism-splitting-layers-across-devices) covered the other way to split a model: not within a layer, but **across layers** — device 0 holds layers 1-8, device 1 holds layers 9-16, and so on, with activations physically handed off from stage to stage. The problem that recap flagged but didn't quantify is the **pipeline bubble**: naively, stage 1 has nothing to do until stage 0 finishes the *current* batch's layers, and stage 0 has nothing to do once it's handed everything off — idle time at both ends of the pipeline. Splitting work into several **micro-batches** and feeding them through the stages one after another keeps more stages busy simultaneously, but never eliminates the bubble entirely; the fraction of idle time is:

```
bubble_fraction ≈ (num_stages - 1) / num_micro_batches
```

More stages means more idle time to fill; more micro-batches in flight means more opportunities to fill it. `example.py` computes this formula for real, across a sweep of `num_micro_batches`.

Here is where inference genuinely diverges from training. **Prefill** processes a whole prompt as one call — its tokens *can* be split into many micro-batches, or several different requests' prefill work can be interleaved, giving the pipeline plenty to fill it with, much like training's large batches do. **Decode**, for a single request, is fundamentally one token at a time: there is no "more micro-batches" available *within one request's own decode step* to hide the bubble with, because there is only ever one token to compute. The formula above still applies, but with `num_micro_batches` collapsing toward 1 for a lone request, the bubble fraction blows up toward `(num_stages - 1)` — i.e. nearly all of every stage's time wasted. The only way pipeline-parallel inference stays efficient during decode is if the *server*, not any single request, supplies enough micro-batches — by batching many **concurrent** requests' decode steps together across the pipeline stages at once, so that while stage 0 computes request A's next token, stage 1 is simultaneously computing request B's. This ties directly back to continuous batching in [Lesson 4 §4](../04-Serving-Frameworks/README.md#4-hugging-face-tgi-continuous-in-flight-batching): pipeline-parallel inference throughput is only as good as the number of concurrent in-flight requests the scheduler keeps the pipeline fed with. `example.py` demonstrates exactly this: `num_micro_batches=1` (one request, one token, nothing to pipeline) leaves a huge bubble; many concurrent decode requests batched together drives the bubble fraction toward zero.

## 4. Data parallelism (recap + inference framing)

[Phase 04 Lesson 3 §2](../../Phase-04-Pretraining-LLMs/03-Distributed-Training-Basics/README.md#2-data-parallelism-dp-the-simplest-form) covered data parallelism for training: replicate the whole model across `N` devices, split the batch across them, and all-reduce gradients to keep every replica in sync. For **inference**, data parallelism is even simpler, because there is no gradient to synchronize at all: replicate the whole model across independent GPU (or GPU-group) replicas, and route different **requests** to different replicas. Once a request is routed, its replica generates its response completely independently — **zero cross-replica communication happens during generation**, unlike every technique in §2-§3, both of which require communication on every forward pass.

This makes DP the simplest lever for scaling inference *throughput* — more replicas simply means more concurrent requests served, with no added per-token latency at all. But it is important to be precise about what DP does **not** solve: if a single replica's model doesn't fit on the GPU(s) available to it in the first place, adding more replicas doesn't help, because each replica still needs the full model. That's a Reason-A memory-capacity problem (§1), and only tensor parallelism or pipeline parallelism can shrink what one replica needs to hold. Real large-model deployments combine both: for instance, tensor-parallelism degree 8 within one node so the model actually fits and each forward pass runs fast (§2), then data-parallelism degree `N` to replicate that whole 8-GPU unit `N` times over, multiplying total concurrent throughput without touching per-request latency at all. The two axes are orthogonal on purpose — TP/PP answer "does one copy of the model run correctly and fast," DP answers "how many copies do we need to run at once."

## 5. Expert parallelism (MoE-specific)

[Phase 03 Lesson 4 §4](../../Phase-03-LLM-Architectures-and-Types/04-Mixture-of-Experts/README.md#4-trade-offs) already flagged that Mixture-of-Experts models introduce a distributed-systems cost dense models don't have: different experts can live on different devices, and since each token's router ([Phase 03 Lesson 4 §2](../../Phase-03-LLM-Architectures-and-Types/04-Mixture-of-Experts/README.md#2-the-router-and-top-k-routing)) may select an expert that isn't local, tokens must be shuffled to reach whichever device holds their assigned expert(s) — an **all-to-all** communication step, once per MoE layer, dispatching tokens out to their experts and then combining the results back.

That lesson framed this as a training-time overhead, but inference has its own, distinctly different failure mode buried inside the same mechanism. During **prefill**, or during training, a batch typically contains many thousands of tokens, and — assuming the load-balancing objective ([Phase 03 Lesson 4 §3](../../Phase-03-LLM-Architectures-and-Types/04-Mixture-of-Experts/README.md#3-the-load-balancing-problem)) is doing its job — those tokens statistically spread their routing decisions across most or all of the available experts, keeping every expert-holding GPU busy. During **decode**, a batch is often just a handful of concurrent requests' single next-token computations — far fewer tokens than there are experts. With so few tokens routing independently to a top-`k` subset of experts each, it becomes entirely plausible that a real batch that step touches only a fraction of the total experts, leaving every GPU holding an *un*touched expert completely idle for that step, doing no useful work at all while still occupying capacity in the deployment. This is a genuinely different failure mode from the pipeline bubble in §3 — the bubble is about *time* stages spend waiting for data to arrive; this is about *entire devices* going unused for a whole step because the batch simply didn't route any work to them. `example.py` simulates this directly with real random routing draws, measuring the fraction of experts (and thus GPUs) touched at all across a range of batch sizes. The practical fixes mirror the diagnosis: batch decode requests aggressively enough that routing statistics start to even back out (tying again to [Lesson 4's continuous batching](../04-Serving-Frameworks/README.md#4-hugging-face-tgi-continuous-in-flight-batching)), or place/replicate experts more cleverly (e.g. duplicating popular experts across more devices) so a small batch is less likely to leave any one expert's *only* copy completely unused.

## 6. Sequence / context parallelism

Every technique so far shards either the **model** (TP splits a weight matrix, PP splits layers, EP splits experts) or the **batch** (DP replicates the whole model across independent request streams). None of them shard the **sequence** itself — but for very long input contexts, [Phase 03 Lesson 6](../../Phase-03-LLM-Architectures-and-Types/06-Long-Context-Techniques/README.md)'s territory, the sequence dimension alone can be the thing that doesn't fit: a long enough prompt's activations and intermediate attention computations during prefill can exceed one GPU's memory or compute budget even for a model whose *weights* fit easily.

**Sequence (or context) parallelism** shards the sequence dimension itself across GPUs during prefill: each GPU holds and computes over only a *slice* of the prompt's tokens, rather than the whole thing. The complication is that self-attention ([Phase 02 Lesson 2](../../Phase-02-Transformer-Architecture-Deep-Dive/02-Self-Attention-and-Multi-Head-Attention/README.md)) needs every query to see every key and value in the sequence, not just the ones in its own slice — so some communication has to make the *full* set of keys/values available to every query without requiring any single GPU to hold the *full* sequence's activations in memory at once. A **ring-attention**-style pattern (Liu, Zaharia & Abbeel, 2023) solves exactly this: arrange the GPUs in a logical ring, and have each one pass its local K/V shard around the ring one hop at a time, so that over the course of the ring's full rotation, every GPU's queries eventually get to attend against every other GPU's keys and values — accumulating the correct attention output incrementally, without ever materializing the whole sequence's K/V on one device.

This is specifically a **prefill-time** (or prompt-processing-time) technique: it addresses a memory/compute limit driven by sequence **length**, which is an entirely different axis from TP's per-layer weight sharding, PP's per-layer-group sharding, DP's per-request replication, or EP's per-expert sharding. In principle nothing stops combining sequence parallelism with any of the others — a very long prompt on a very large model could need sequence parallelism to process the prompt *and* tensor/pipeline parallelism to hold the model — but the two problems (sequence length vs. model size) are independent, and sequence parallelism is the one lever in this lesson that directly targets the former.

## 7. Putting it together

| Parallelism | What's sharded | Communication required | Problem it solves | Prefill vs. decode behavior |
|---|---|---|---|---|
| **Tensor (TP)** | Individual weight matrices (attention heads, FFN intermediate dim) | All-reduce / all-gather of activations, on **every** forward pass | Model doesn't fit / runs too slow on one GPU | Same mechanism both phases; latency-critical every decode step, so usually confined to fast intra-node links |
| **Pipeline (PP)** | Layers, grouped into stages | Activations handed off stage-to-stage | Model doesn't fit across enough layers for one GPU | Prefill can fill the pipeline with micro-batches; a single request's decode has none, needs concurrent requests to fill it instead |
| **Data (DP)** | Nothing — the whole model is replicated | None during generation (routing only) | Too slow / too little throughput on one replica | Identical behavior both phases; scales concurrent requests, not per-request speed |
| **Expert (EP)** | Individual experts (MoE layers only) | All-to-all token dispatch/combine, every MoE layer | Expert weights spread across devices; compute-per-token stays sparse | Prefill's large batches spread load across most experts; decode's small batches can leave many experts/GPUs idle |
| **Sequence / context (SP)** | The sequence dimension itself | Ring-style K/V exchange across shards | Very long prompts don't fit in memory/compute even if the model does | Prefill-time only — decode's one-token-at-a-time steps have no long sequence to shard |

No real large-scale deployment picks just one row of this table — a frontier-scale model typically combines tensor parallelism within a node (§2), pipeline parallelism across a small number of nodes if layers still don't fit on one node's TP group (§3), data parallelism to replicate that whole unit for throughput (§4), expert parallelism if the model is MoE (§5), and sequence parallelism specifically for requests with unusually long prompts (§6) — the same "compose several axes" lesson [Phase 04 Lesson 3 §6](../../Phase-04-Pretraining-LLMs/03-Distributed-Training-Basics/README.md#6-how-real-training-combines-all-of-these) already drew for training, just with a different mix of axes and a very different sensitivity to per-step latency now that real users are waiting on the other end.
