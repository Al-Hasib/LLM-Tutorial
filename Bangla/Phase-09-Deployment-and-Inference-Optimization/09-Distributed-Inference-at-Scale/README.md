# Distributed Inference at Scale

**Phase:** [Deployment and Inference Optimization](../README.md) · **Topic folder:** `09-Distributed-Inference-at-Scale`

## কেন এটি গুরুত্বপূর্ণ

এই phase-এর এখন পর্যন্ত প্রতিটি lesson অন্তর্নিহিতভাবে ধরে নিয়েছে যে পুরো model **একটি** GPU-তে ধরে যায় ও চলে: [Lesson 2](../02-Quantization/README.md) weights-কে আরও ভালোভাবে ধরানোর জন্য সংকুচিত করে, [Lesson 3](../03-KV-Cache-and-Speculative-Decoding/README.md) একটি GPU-কে যে redundant কাজ করতে হয় তা কমায়, [Lesson 4](../04-Serving-Frameworks/README.md) সেই একটি GPU-তে request-গুলো দক্ষতার সাথে schedule করে — কিন্তু এখন পর্যন্ত কোথাও model-কে নিজেই একাধিক device জুড়ে *বিস্তৃত* হতে হয়নি। Model যথেষ্ট বড় হলে সেই অনুমান দুটি সত্যিকারের আলাদা উপায়ে ভেঙে যায়। প্রথমত, weights এবং KV cache একটি GPU-র HBM-এ একেবারেই **ধরে না** — কয়েকশো billion parameter-এর একটি model-এর জন্য [Lesson 1 §2](../01-GPU-and-Hardware-Fundamentals/README.md#2-the-memory-hierarchy-hbm-vs-sram)-এর "কয়েক দশ gigabyte" সীমা একটি কঠিন দেয়াল, কোনো নরম অসুবিধা নয়। দ্বিতীয়ত, এটি *ধরে গেলেও*, একটি GPU-র peak FLOPs ও memory bandwidth throughput বা latency-কে একটি বাস্তব deployment-এর প্রয়োজনের অনেক নিচে সীমাবদ্ধ করে দিতে পারে, memory-তে জায়গা যতই থাকুক। [Phase 04 Lesson 3](../../Phase-04-Pretraining-LLMs/03-Distributed-Training-Basics/README.md) ইতিমধ্যে data, tensor, এবং pipeline parallelism পরিচয় করিয়েছে — কিন্তু **training**-এর জন্য। এই lesson স্পষ্টভাবে সেই তিনটি ধারণার recap করে (আবার derive করে না) এবং দেখায় workload যখন **inference**, তখন প্রতিটি কীভাবে ভিন্ন আচরণ করে, বিশেষত autoregressive decode-এর এক-সময়ে-একটি-token ক্রমিক নির্ভরতার কারণে, যা training-কালের বেশ কয়েকটি অনুমান সরাসরি ভেঙে দেয় (যেমন, pipeline bubble লুকানোর জন্য বড় micro-batch সংখ্যা একটি একক request-এর decode-এর ভেতরে সহজভাবেই পাওয়া যায় না)। এরপর এটি parallelism-এর আরও দুটি রূপ কভার করে যা training-এ একইভাবে দরকার হয় না: **expert parallelism** (বিভিন্ন device-এ ছড়িয়ে থাকা expert-দের কাছে token route করা, [Phase 03 Lesson 4](../../Phase-03-LLM-Architectures-and-Types/04-Mixture-of-Experts/README.md)-এর এলাকা) এবং **sequence/context parallelism** (prefill-এর সময় একটি খুব দীর্ঘ input-কে একাধিক GPU জুড়ে ভাগ করা)।

## এই lesson যা কভার করে

- Inference distribute করার দুটি স্বাধীন কারণ: ধরে না বনাম খুব ধীর, এবং কেন সমাধান নির্ভর করে আপনার আসলে কোনটি আছে তার উপর
- Tensor parallelism, inference-এর জন্য recap ও নতুনভাবে দেখা: কেন এর communication প্রতি training step-এ একবার নয়, *প্রতিটি* forward pass-এ ঘটে, এবং কেন তা এটিকে দ্রুত intra-node interconnect-এ বেঁধে রাখে
- Pipeline parallelism, inference-এর জন্য recap ও নতুনভাবে দেখা: bubble formula, এবং কেন decode-এর কাছে এটি লুকানোর মতো কোনো "অতিরিক্ত micro-batch" নেই, যদি না server-এ যথেষ্ট একযোগে চলা request থাকে
- Data parallelism, inference-এর জন্য recap ও নতুনভাবে দেখা: scaling-এর সবচেয়ে সহজ lever, এবং এটি কী ঠিক *করে না*
- Expert parallelism: MoE-এর all-to-all dispatch, এবং ছোট decode batch যেভাবে নির্দিষ্টভাবে expert-ধারী GPU-গুলোকে অলস রেখে দেয়
- Sequence / context parallelism: খুব দীর্ঘ prompt-এর জন্য sequence dimension-কেই GPU জুড়ে shard করা
- পাঁচটি parallelism strategy পাশাপাশি তুলনা করে একটি recap table

## 1. Inference distribute করার দুটি স্বাধীন কারণ

নিচের কোনো যন্ত্রপাতির দিকে হাত বাড়ানোর আগে, একটি GPU *কেন* যথেষ্ট নয় সে সম্পর্কে সুনির্দিষ্ট হওয়া দরকার, কারণ দুটি সম্ভাব্য কারণের জন্য সম্পূর্ণ ভিন্ন সমাধান লাগে।

**Reason A: এটি ধরে না।** একটি বড় model-এর parameter, সাথে server-কে যতগুলো একযোগে চলা sequence ধরে রাখতে হয় তাদের KV cache ([Lesson 3 §3](../03-KV-Cache-and-Speculative-Decoding/README.md#3-the-kv-cache-pay-for-each-tokens-kv-exactly-once)), একটি accelerator-এ উপলব্ধ কয়েক দশ gigabyte HBM-কে সহজেই ছাড়িয়ে যেতে পারে ([Lesson 1 §2](../01-GPU-and-Hardware-Fundamentals/README.md#2-the-memory-hierarchy-hbm-vs-sram))। Scheduling-এর কোনো চাতুর্যই এটি ঠিক করতে পারে না — byte-গুলোকে কোথাও না কোথাও থাকতে হবে, এবং একটি device-এ না ধরলে সেগুলোকে কয়েকটিতে ভাগ করতেই হবে। এটি একটি **memory-capacity** সমস্যা।

**Reason B: এটি খুব ধীর।** একটি GPU-তে স্বাচ্ছন্দ্যে ধরে যায় এমন model-ও একটি deployment-এর প্রয়োজনীয় latency বা throughput-এর জন্য খুব ধীর হতে পারে: একটি GPU-র peak FLOPs prefill কত দ্রুত চলতে পারে তা সীমাবদ্ধ করে, এবং এর memory bandwidth decode কত দ্রুত চলতে পারে তা সীমাবদ্ধ করে ([Lesson 1 §6](../01-GPU-and-Hardware-Fundamentals/README.md#6-the-payoff-why-prefill-is-compute-bound-and-decode-is-memory-bound))। এটি একটি **speed/throughput** সমস্যা, এবং memory capacity কোনো সমস্যা না হলেও এটি থাকে।

এই পার্থক্য কেন গুরুত্বপূর্ণ: সমাধানগুলো পরস্পর বিনিময়যোগ্য নয়। Reason A-র সমাধান হলো *model*-কে device জুড়ে ভাগ করা — tensor parallelism (§2) বা pipeline parallelism (§3) — যাতে প্রতিটি device-কে weights-এর শুধু একটি ভগ্নাংশ ধরে রাখতে হয়। Reason B, যখন memory ইতিমধ্যে ধরে যায়, প্রায়ই সহজভাবে পুরো model replicate করে সমান্তরালে আরও request serve করে ভালোভাবে সমাধান হয় — data parallelism (§4) — যা memory capacity-র জন্য কিছুই করে না কিন্তু সরাসরি throughput গুণিত করে। ভুল tool বেছে নেওয়া (যেমন, শুধু বেশি throughput পেতে একটি GPU-তে ইতিমধ্যে ধরে যাওয়া model-কে tensor-parallelize করা) কোনো capacity সুবিধা ছাড়াই communication overhead যোগ করে, যা একটি দ্বিতীয় পূর্ণ replica আরও সহজে সমাধান করত। বাস্তব বড়-model deployment-এ সাধারণত দুটি সমস্যাই একসাথে সমাধান করতে হয়, আর ঠিক এই কারণেই §2-§6 একত্রিত হয়।

## 2. Tensor parallelism (recap + inference-এর দৃষ্টিকোণ)

[Phase 04 Lesson 3 §3](../../Phase-04-Pretraining-LLMs/03-Distributed-Training-Basics/README.md#3-tensor--model-parallelism-splitting-individual-layers) ইতিমধ্যে mechanism-টি কভার করেছে: একটি একক weight matrix-কে column-wise (বা row-wise) device জুড়ে ভাগ করো, যাতে প্রতিটি device সেই layer-এর parameter-এর শুধু একটি *ভগ্নাংশ* ধরে রাখে ও তা দিয়ে গণনা করে। একটি Transformer block-এর ভেতরে প্রয়োগ করলে, এর সাধারণ অর্থ হলো attention projection-কে head group জুড়ে ভাগ করা (প্রতিটি device attention head-এর একটি subset-এর মালিক) এবং FFN-এর intermediate dimension-কে ([Phase 02 Lesson 5 §5](../../Phase-02-Transformer-Architecture-Deep-Dive/05-LayerNorm-Residuals-FFN/README.md#5-the-position-wise-feed-forward-network-ffn)) দুটি device জুড়ে অর্ধেক করে ভাগ করা, যেখানে প্রতিটি device নিজের আংশিক output গণনা করে:

```
device 0: partial_out_0 = X @ W_1        (W_1 = first half of the sharded weight matrix)
device 1: partial_out_1 = X @ W_2        (W_2 = second half)
combine:  full_out = all_reduce(partial_out_0, partial_out_1)   -- or an all-gather, depending on the split
```

Mechanism-টি training-এর মতোই অভিন্ন। **Inference**-এর জন্য যা বদলায় তা হলো সেই combine step-টি *কত ঘন ঘন* ঘটতে হয়, এবং ধীর হলে এটি কতটা সংবেদনশীল। Training-এ model প্রতি optimizer step-এ একবার একটি বড় batch-এর উপর একটি forward ও backward pass চালায় — all-reduce/all-gather খরচ প্রকৃত, কিন্তু প্রতিবার ঘটার সময় প্রচুর উপযোগী compute-এর উপর amortize হয়ে যায়। Inference-এ sharded layer **প্রতিটি একক forward pass**-এ চলে — prefill, এবং তারপর একটি request-এর পরবর্তী (সম্ভাব্য কয়েকশো) decode step-এর প্রতিটিতে — তাই এই communication কোনো বিরল, amortize করার যোগ্য ঘটনা নয়, এটি প্রতিটি request-এর generation-এর প্রতিটি ধাপে দেওয়া একটি পুনরাবৃত্ত কর। যেহেতু decode-step latency ([Lesson 3 §7](../03-KV-Cache-and-Speculative-Decoding/README.md#7-ttft-and-itl-the-two-per-request-latency-metrics)-এর ITL) সেই metric যা user সরাসরি অনুভব করেন, এই communication-কে **low-latency** হতে হবে, শুধু high-bandwidth নয়: একটি physical node-এর ভেতরে NVLink-শ্রেণির interconnect যোগ হওয়া latency-কে যথেষ্ট ছোট রাখে যাতে এটি লাভজনক হয়, কিন্তু node-এর *মধ্য দিয়ে* tensor parallelism (সাধারণ networking, এক order of magnitude বেশি latency) সাধারণত inference-এর জন্য একটি খারাপ বিনিময় — পুরো একটি request-এর per-token latency এখন একটি network round trip-এর উপর নির্ভর করে, যা training-এর amortized-per-step communication-কে কখনো এই ঘনত্বে সহ্য করতে হয়নি। এটিই মূল কারণ যে inference-এর জন্য tensor parallelism প্রায় সবসময় একটি cluster জুড়ে না ছড়িয়ে একটি server-এর GPU-গুলোর *ভেতরে* সীমাবদ্ধ রাখা হয়।

## 3. Pipeline parallelism (recap + inference-এর দৃষ্টিকোণ)

[Phase 04 Lesson 3 §4](../../Phase-04-Pretraining-LLMs/03-Distributed-Training-Basics/README.md#4-pipeline-parallelism-splitting-layers-across-devices) একটি model ভাগ করার অন্য উপায়টি কভার করেছে: একটি layer-এর ভেতরে নয়, বরং **layer-গুলোর মধ্য দিয়ে** — device 0 ধরে layer 1-8, device 1 ধরে layer 9-16, ইত্যাদি, যেখানে activation-গুলো stage থেকে stage-এ physically হস্তান্তর হয়। সেই recap যে সমস্যাটি চিহ্নিত করেছিল কিন্তু পরিমাপ করেনি তা হলো **pipeline bubble**: naive-ভাবে, stage 0 *বর্তমান* batch-এর layer শেষ না করা পর্যন্ত stage 1-এর কিছু করার নেই, এবং stage 0 সবকিছু হস্তান্তর করে দেওয়ার পর তার কিছু করার নেই — pipeline-এর দুই প্রান্তেই অলস সময়। কাজকে কয়েকটি **micro-batch**-এ ভাগ করে সেগুলোকে একের পর এক stage-এর মধ্য দিয়ে খাওয়ালে একসাথে আরও বেশি stage ব্যস্ত থাকে, কিন্তু bubble কখনো পুরোপুরি দূর হয় না; অলস সময়ের ভগ্নাংশ হলো:

```
bubble_fraction ≈ (num_stages - 1) / num_micro_batches
```

বেশি stage মানে পূরণ করার মতো বেশি অলস সময়; চলমান বেশি micro-batch মানে তা পূরণ করার বেশি সুযোগ। `example.py` `num_micro_batches`-এর একটি sweep জুড়ে এই formula সত্যিই গণনা করে।

এখানেই inference সত্যিকারভাবে training থেকে আলাদা হয়ে যায়। **Prefill** পুরো একটি prompt-কে একটি call হিসেবে প্রসেস করে — এর token-গুলোকে অনেক micro-batch-এ ভাগ *করা যায়*, অথবা কয়েকটি ভিন্ন request-এর prefill কাজ মিশিয়ে চালানো যায়, pipeline-কে পূরণ করার মতো প্রচুর কিছু দিয়ে, অনেকটা training-এর বড় batch-এর মতো। **Decode**, একটি একক request-এর জন্য, মৌলিকভাবে এক-সময়ে-একটি-token: bubble লুকানোর জন্য *একটি request-এর নিজস্ব decode step-এর ভেতরে* কোনো "আরও micro-batch" নেই, কারণ গণনা করার জন্য সবসময় শুধু একটি token থাকে। উপরের formula এখনও প্রযোজ্য, কিন্তু একটি একক request-এর জন্য `num_micro_batches` 1-এর দিকে নেমে আসায় bubble fraction `(num_stages - 1)`-এর দিকে ফুলে ওঠে — অর্থাৎ প্রতিটি stage-এর প্রায় সব সময় নষ্ট। Decode-এর সময় pipeline-parallel inference দক্ষ থাকার একমাত্র উপায় হলো যদি *server*, কোনো একক request নয়, যথেষ্ট micro-batch সরবরাহ করে — অনেকগুলো **একযোগে চলা** request-এর decode step pipeline stage জুড়ে একসাথে batch করে, যাতে stage 0 যখন request A-র পরবর্তী token গণনা করছে, stage 1 একই সময়ে request B-র token গণনা করছে। এটি সরাসরি [Lesson 4 §4](../04-Serving-Frameworks/README.md#4-hugging-face-tgi-continuous-in-flight-batching)-এর continuous batching-এর সাথে যুক্ত: pipeline-parallel inference throughput ঠিক ততটাই ভালো যতগুলো একযোগে চলমান request দিয়ে scheduler pipeline-কে খাওয়াতে পারে। `example.py` ঠিক এটিই দেখায়: `num_micro_batches=1` (একটি request, একটি token, pipeline করার কিছু নেই) একটি বিশাল bubble রেখে যায়; অনেকগুলো একযোগে চলা decode request একসাথে batch করলে bubble fraction শূন্যের দিকে নেমে আসে।

## 4. Data parallelism (recap + inference-এর দৃষ্টিকোণ)

[Phase 04 Lesson 3 §2](../../Phase-04-Pretraining-LLMs/03-Distributed-Training-Basics/README.md#2-data-parallelism-dp-the-simplest-form) training-এর জন্য data parallelism কভার করেছে: পুরো model `N` টি device জুড়ে replicate করো, batch-কে তাদের মধ্যে ভাগ করো, এবং প্রতিটি replica-কে sync-এ রাখতে gradient all-reduce করো। **Inference**-এর জন্য data parallelism আরও সহজ, কারণ sync করার মতো কোনো gradient-ই নেই: পুরো model-কে স্বাধীন GPU (বা GPU-group) replica জুড়ে replicate করো, এবং ভিন্ন ভিন্ন **request**-কে ভিন্ন ভিন্ন replica-তে route করো। একবার একটি request route হয়ে গেলে, এর replica সম্পূর্ণ স্বাধীনভাবে তার response তৈরি করে — **generation-এর সময় শূন্য cross-replica communication ঘটে**, §2-§3-এর প্রতিটি কৌশলের বিপরীতে, যেগুলোর দুটিতেই প্রতিটি forward pass-এ communication লাগে।

এটি DP-কে inference *throughput* scale করার সবচেয়ে সহজ lever বানায় — বেশি replica মানে সহজভাবে বেশি একযোগে request serve করা, কোনো অতিরিক্ত per-token latency ছাড়াই। কিন্তু DP কী সমাধান **করে না** সে সম্পর্কে সুনির্দিষ্ট হওয়া গুরুত্বপূর্ণ: একটি একক replica-র model যদি প্রথমত তার জন্য উপলব্ধ GPU(s)-এ না ধরে, তাহলে আরও replica যোগ করলে কোনো লাভ নেই, কারণ প্রতিটি replica-র এখনও পূর্ণ model দরকার। এটি একটি Reason-A memory-capacity সমস্যা (§1), এবং শুধু tensor parallelism বা pipeline parallelism-ই একটি replica-কে যা ধরে রাখতে হয় তা সংকুচিত করতে পারে। বাস্তব বড়-model deployment দুটিকে একত্র করে: যেমন, একটি node-এর ভেতরে tensor-parallelism degree 8, যাতে model আসলে ধরে যায় এবং প্রতিটি forward pass দ্রুত চলে (§2), তারপর data-parallelism degree `N`, সেই পুরো 8-GPU ইউনিটকে `N` বার replicate করতে, per-request latency একটুও না ছুঁয়ে মোট একযোগে throughput গুণিত করে। দুটি অক্ষ ইচ্ছাকৃতভাবেই orthogonal — TP/PP উত্তর দেয় "model-এর একটি copy কি সঠিকভাবে ও দ্রুত চলে," DP উত্তর দেয় "একসাথে কতগুলো copy চালাতে হবে।"

## 5. Expert parallelism (MoE-নির্দিষ্ট)

[Phase 03 Lesson 4 §4](../../Phase-03-LLM-Architectures-and-Types/04-Mixture-of-Experts/README.md#4-trade-offs) ইতিমধ্যে চিহ্নিত করেছে যে Mixture-of-Experts model এমন একটি distributed-systems খরচ নিয়ে আসে যা dense model-এর নেই: ভিন্ন ভিন্ন expert ভিন্ন ভিন্ন device-এ থাকতে পারে, এবং যেহেতু প্রতিটি token-এর router ([Phase 03 Lesson 4 §2](../../Phase-03-LLM-Architectures-and-Types/04-Mixture-of-Experts/README.md#2-the-router-and-top-k-routing)) এমন একটি expert বেছে নিতে পারে যা local নয়, token-গুলোকে এলোমেলো করে পাঠাতে হয় যাতে সেগুলো তাদের নির্ধারিত expert(s) ধারণকারী device-এ পৌঁছায় — একটি **all-to-all** communication step, প্রতি MoE layer-এ একবার, token-গুলোকে তাদের expert-এর কাছে dispatch করে এবং তারপর ফলাফল আবার একত্র করে।

সেই lesson এটিকে একটি training-কালের overhead হিসেবে দেখিয়েছিল, কিন্তু একই mechanism-এর ভেতরে inference-এর নিজস্ব, স্পষ্টভাবে ভিন্ন একটি failure mode লুকিয়ে আছে। **Prefill**-এর সময়, বা training-এর সময়, একটি batch-এ সাধারণত হাজার হাজার token থাকে, এবং — ধরে নিয়ে যে load-balancing objective ([Phase 03 Lesson 4 §3](../../Phase-03-LLM-Architectures-and-Types/04-Mixture-of-Experts/README.md#3-the-load-balancing-problem)) তার কাজ করছে — সেই token-গুলো statistically তাদের routing সিদ্ধান্ত উপলব্ধ বেশিরভাগ বা সব expert-এর মধ্যে ছড়িয়ে দেয়, প্রতিটি expert-ধারী GPU-কে ব্যস্ত রাখে। **Decode**-এর সময়, একটি batch প্রায়ই শুধু কয়েকটি একযোগে চলা request-এর একক পরবর্তী-token গণনা — expert-এর সংখ্যার চেয়ে অনেক কম token। এত কম token প্রত্যেকে স্বাধীনভাবে expert-এর একটি top-`k` subset-এ route হওয়ায়, এটি সম্পূর্ণ সম্ভব যে সেই ধাপে একটি প্রকৃত batch মোট expert-এর শুধু একটি ভগ্নাংশ স্পর্শ করে, এবং একটি *অস্পর্শিত* expert ধারণকারী প্রতিটি GPU সেই ধাপে সম্পূর্ণ অলস থাকে, কোনো উপযোগী কাজ না করেও deployment-এ capacity দখল করে রাখে। এটি §3-এর pipeline bubble থেকে সত্যিকারভাবে ভিন্ন একটি failure mode — bubble হলো data আসার জন্য stage-গুলো অপেক্ষায় যে *সময়* কাটায় তা নিয়ে; এটি হলো *পুরো device* একটি পুরো ধাপের জন্য অব্যবহৃত থাকা, কারণ batch সহজভাবেই তাদের কাছে কোনো কাজ route করেনি। `example.py` প্রকৃত random routing draw দিয়ে এটি সরাসরি simulate করে, বিভিন্ন batch size জুড়ে expert-এর (এবং তাই GPU-র) কত ভগ্নাংশ আদৌ স্পর্শিত হয় তা মেপে। ব্যবহারিক সমাধানগুলো রোগনির্ণয়েরই প্রতিফলন: decode request-গুলোকে যথেষ্ট আক্রমণাত্মকভাবে batch করা যাতে routing statistics আবার সমান হতে শুরু করে (আবার [Lesson 4-এর continuous batching](../04-Serving-Frameworks/README.md#4-hugging-face-tgi-continuous-in-flight-batching)-এর সাথে যুক্ত), অথবা expert-দের আরও চতুরভাবে place/replicate করা (যেমন জনপ্রিয় expert-দের আরও বেশি device-এ duplicate করা) যাতে একটি ছোট batch-এর কারণে কোনো একটি expert-এর *একমাত্র* copy সম্পূর্ণ অব্যবহৃত থাকার সম্ভাবনা কম থাকে।

## 6. Sequence / context parallelism

এখন পর্যন্ত প্রতিটি কৌশল হয় **model**-কে shard করে (TP একটি weight matrix ভাগ করে, PP layer ভাগ করে, EP expert ভাগ করে) অথবা **batch**-কে (DP পুরো model-কে স্বাধীন request stream জুড়ে replicate করে)। এর কোনোটিই **sequence**-কে নিজে shard করে না — কিন্তু খুব দীর্ঘ input context-এর জন্য, [Phase 03 Lesson 6](../../Phase-03-LLM-Architectures-and-Types/06-Long-Context-Techniques/README.md)-এর এলাকা, শুধু sequence dimension-ই সেই জিনিস হতে পারে যা ধরে না: একটি যথেষ্ট দীর্ঘ prompt-এর activation এবং prefill-এর সময় মধ্যবর্তী attention গণনা একটি GPU-র memory বা compute budget ছাড়িয়ে যেতে পারে, এমনকি এমন model-এর জন্যও যার *weights* সহজেই ধরে যায়।

**Sequence (বা context) parallelism** prefill-এর সময় sequence dimension-কেই GPU জুড়ে shard করে: প্রতিটি GPU পুরোটার বদলে prompt-এর token-গুলোর শুধু একটি *slice* ধরে রাখে ও তার উপর গণনা করে। জটিলতা হলো self-attention ([Phase 02 Lesson 2](../../Phase-02-Transformer-Architecture-Deep-Dive/02-Self-Attention-and-Multi-Head-Attention/README.md))-এ প্রতিটি query-কে sequence-এর প্রতিটি key ও value দেখতে হয়, শুধু নিজের slice-এরগুলো নয় — তাই কিছু communication-কে প্রতিটি query-র কাছে key/value-এর *পূর্ণ* set উপলব্ধ করতে হয়, কোনো একক GPU-কে একসাথে *পূর্ণ* sequence-এর activation memory-তে রাখতে বাধ্য না করে। একটি **ring-attention**-style pattern (Liu, Zaharia & Abbeel, 2023) ঠিক এটিই সমাধান করে: GPU-গুলোকে একটি logical ring-এ সাজাও, এবং প্রতিটিকে তার local K/V shard ring-এর চারপাশে এক hop করে পাঠাতে দাও, যাতে ring-এর পূর্ণ ঘূর্ণনের মধ্যে প্রতিটি GPU-র query শেষ পর্যন্ত অন্য প্রতিটি GPU-র key ও value-এর বিরুদ্ধে attend করতে পারে — ধাপে ধাপে সঠিক attention output জমা করে, কখনো পুরো sequence-এর K/V একটি device-এ materialize না করে।

এটি নির্দিষ্টভাবে একটি **prefill-কালের** (বা prompt-processing-কালের) কৌশল: এটি sequence **length** দ্বারা চালিত একটি memory/compute সীমা মোকাবিলা করে, যা TP-র per-layer weight sharding, PP-র per-layer-group sharding, DP-র per-request replication, বা EP-র per-expert sharding থেকে সম্পূর্ণ ভিন্ন একটি অক্ষ। নীতিগতভাবে sequence parallelism-কে অন্য যেকোনোটির সাথে একত্র করতে কিছুই বাধা দেয় না — একটি খুব বড় model-এ একটি খুব দীর্ঘ prompt-এর জন্য prompt প্রসেস করতে sequence parallelism *এবং* model ধরে রাখতে tensor/pipeline parallelism দরকার হতে পারে — কিন্তু দুটি সমস্যা (sequence length বনাম model size) স্বাধীন, এবং এই lesson-এ sequence parallelism-ই একমাত্র lever যা সরাসরি প্রথমটিকে লক্ষ্য করে।

## 7. সবকিছু একসাথে

| Parallelism | কী shard করা হয় | প্রয়োজনীয় communication | যে সমস্যা সমাধান করে | Prefill বনাম decode আচরণ |
|---|---|---|---|---|
| **Tensor (TP)** | একক weight matrix (attention head, FFN intermediate dim) | Activation-এর all-reduce / all-gather, **প্রতিটি** forward pass-এ | Model একটি GPU-তে ধরে না / খুব ধীর চলে | দুই phase-এ একই mechanism; প্রতিটি decode step-এ latency-critical, তাই সাধারণত দ্রুত intra-node link-এ সীমাবদ্ধ |
| **Pipeline (PP)** | Layer, stage-এ গ্রুপ করা | Stage থেকে stage-এ activation হস্তান্তর | যথেষ্ট layer জুড়ে model একটি GPU-তে ধরে না | Prefill micro-batch দিয়ে pipeline পূরণ করতে পারে; একটি একক request-এর decode-এর কোনোটি নেই, পরিবর্তে পূরণ করতে একযোগে চলা request লাগে |
| **Data (DP)** | কিছুই না — পুরো model replicate করা | Generation-এর সময় কিছু নেই (শুধু routing) | একটি replica-তে খুব ধীর / খুব কম throughput | দুই phase-এ অভিন্ন আচরণ; একযোগে request scale করে, per-request গতি নয় |
| **Expert (EP)** | একক expert (শুধু MoE layer) | All-to-all token dispatch/combine, প্রতিটি MoE layer-এ | Expert weights device জুড়ে ছড়ানো; প্রতি-token compute sparse থাকে | Prefill-এর বড় batch বেশিরভাগ expert জুড়ে load ছড়ায়; decode-এর ছোট batch অনেক expert/GPU-কে অলস রাখতে পারে |
| **Sequence / context (SP)** | Sequence dimension নিজেই | Shard জুড়ে ring-style K/V বিনিময় | Model ধরলেও খুব দীর্ঘ prompt memory/compute-এ ধরে না | শুধু prefill-কালে — decode-এর এক-সময়ে-একটি-token ধাপে shard করার মতো কোনো দীর্ঘ sequence নেই |

কোনো বাস্তব বড়-scale deployment এই table-এর শুধু একটি row বেছে নেয় না — একটি frontier-scale model সাধারণত একত্র করে একটি node-এর ভেতরে tensor parallelism (§2), layer যদি এখনও একটি node-এর TP group-এ না ধরে তাহলে অল্প কয়েকটি node জুড়ে pipeline parallelism (§3), throughput-এর জন্য সেই পুরো ইউনিট replicate করতে data parallelism (§4), model MoE হলে expert parallelism (§5), এবং অস্বাভাবিক দীর্ঘ prompt-যুক্ত request-এর জন্য নির্দিষ্টভাবে sequence parallelism (§6) — সেই একই "কয়েকটি অক্ষ compose করো" শিক্ষা যা [Phase 04 Lesson 3 §6](../../Phase-04-Pretraining-LLMs/03-Distributed-Training-Basics/README.md#6-how-real-training-combines-all-of-these) ইতিমধ্যে training-এর জন্য টেনেছে, শুধু অক্ষগুলোর একটি ভিন্ন মিশ্রণ এবং per-step latency-র প্রতি একটি অনেক ভিন্ন সংবেদনশীলতা নিয়ে, এখন যেহেতু অপর প্রান্তে প্রকৃত user অপেক্ষা করছেন।
