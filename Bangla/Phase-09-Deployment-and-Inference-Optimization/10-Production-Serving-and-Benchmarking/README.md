# Production Serving এবং Benchmarking

**Phase:** [Deployment and Inference Optimization](../README.md) · **Topic folder:** `10-Production-Serving-and-Benchmarking`

## কেন এটি গুরুত্বপূর্ণ

[Lesson 4](../04-Serving-Frameworks/README.md) কভার করেছে কীভাবে *একটি* serving process — vLLM, TGI, SGLang, যা-ই হোক — একটি একক GPU fleet-এ KV-cache memory পরিচালনা করে এবং request-গুলো দক্ষতার সাথে batch করে। এটি প্রয়োজনীয়, কিন্তু একটি প্রকৃত production system-এর জন্য মোটেও যথেষ্ট নয়: একটি একক process, যত ভালোভাবেই batch করুক, তার ধারণক্ষমতা ছাড়িয়ে যাওয়া traffic burst-এর বিরুদ্ধে কোনো সুরক্ষা রাখে না, একটি বাস্তব deployment-এর প্রয়োজনীয় ওই process-এর বহু replica জুড়ে load ছড়িয়ে দেওয়ার কোনো উপায় রাখে না, দিনভর চাহিদা বাড়া-কমার সাথে সেই replica-র সংখ্যা বাড়ানো বা কমানোর কোনো উপায় রাখে না, এবং এটি চালানো কারো জন্য এটি আসলে সুস্থ কিনা তা জানার কোনো অন্তর্নির্মিত উপায়ও রাখে না। এই lesson হলো Lesson 4-এর serving process-এর *চারপাশে* জড়ানো সেই layer যা একে বাস্তব, অপ্রত্যাশিত, multi-tenant traffic নির্ভরযোগ্যভাবে serve করা একটি system-এ পরিণত করে: এর সামনে bounded queues ও admission control, এর বহু replica জুড়ে load balancing, সেই replica-সংখ্যার autoscaling, এবং এই যন্ত্রপাতির কোনোটি আদৌ কাজ করছে কিনা তা বলার জন্য প্রয়োজনীয় observability metrics। পথে এটি সেই standard metric vocabulary-ও সম্পূর্ণ করে যা এই পুরো phase গড়ে তুলছে: [Lesson 3 §7](../03-KV-Cache-and-Speculative-Decoding/README.md#7-ttft-and-itl-the-two-per-request-latency-metrics) ইতিমধ্যে TTFT ও ITL উপস্থাপন করেছে, prefill ও decode প্রত্যেকের তৈরি করা দুটি per-request latency সংখ্যা; এই lesson সেই vocabulary-তে TPOT, throughput, concurrency, এবং GPU utilization যোগ করে — ঠিক সেই metrics যেগুলো *দিয়ে* [Lesson 6](../06-Cost-and-Latency-Optimization/README.md)-এর cost/latency trade-off-গুলো মাপা হয়।

## এই lesson যা কভার করে

- একটি খালি inference process-এর production system হয়ে উঠতে কী কী অনুপস্থিত
- Bounded request queues, admission control, এবং load shedding
- Priority queues ও classes, যাতে একটি traffic class অন্যটির latency SLO-কে অনাহারে রাখতে না পারে
- Replica-গুলো জুড়ে load balancing: round-robin, least-outstanding-requests, এবং prefix-aware routing
- বাস্তব signal-এর উপর autoscaling (queue depth, p99 latency, GPU utilization) এবং LLM-নির্দিষ্ট cold-start সমস্যা
- সম্পূর্ণ standard benchmarking vocabulary: TTFT, ITL, TPOT, throughput, concurrency, GPU utilization — নির্ভুলভাবে সংজ্ঞায়িত, formula-সহ
- Multi-tenancy, noisy-neighbor সমস্যা, এবং একটি অমীমাংসিত isolation-বনাম-utilization trade-off হিসেবে per-tenant SLOs/quotas
- Request/response API surface নিজেই: কেন বিশেষভাবে একটি LLM-এর জন্য streaming গুরুত্বপূর্ণ, এবং কীভাবে OpenAI-compatible chat-completions schema de facto interface হয়ে উঠল
- `example.py`: bounded-queue admission control, least-outstanding-requests বনাম round-robin load balancing-এর simulation, এবং simulated per-token timestamps থেকে গণনা করা প্রকৃত metrics

## 1. একটি model process থেকে একটি production system

[Lesson 4](../04-Serving-Frameworks/README.md)-এর সবকিছু ঘটে একটি serving process-এর *ভেতরে*: এটি request গ্রহণ করে, KV-cache memory দক্ষতার সাথে page করে, এবং বর্তমানে in flight যা আছে তা batch করে (continuously, chunked prefill-সহ)। তবে বাস্তব, internet-scale traffic কেবল ওই process-এর দিকে তাক করলে, চারটি ফাঁক সঙ্গে সঙ্গে দেখা দেয়:

- **Overload-এর বিরুদ্ধে কোনো সুরক্ষা নেই।** Process যত দ্রুত serve করতে পারে তার চেয়ে দ্রুত request এলে কী হয়? Lesson 4-এর scheduling logic-এর কিছুই এর উত্তর দেয় না — এটি ধরে নেয় request-গুলো ইতিমধ্যে queue-তে আছে এবং admit হওয়ার জন্য প্রস্তুত, queue-টিরই যে সীমা দরকার হতে পারে তা নয়।
- **GPU-গুলো জুড়ে load ছড়ানোর কোনো উপায় নেই।** একটি process, যত ভালোভাবেই batch করুক, তার নিজের GPU(s)-এর throughput-এ গিয়ে থেমে যায়। প্রকৃত capacity আসে বহু GPU-তে চলা ওই process-এর *বহু* replica থেকে, এবং প্রতিটি আগত request কোন replica-তে যাবে তা কাউকে না কাউকে ঠিক করতে হয়।
- **Capacity বাড়ানো বা কমানোর কোনো উপায় নেই।** একটি স্থির সংখ্যক replica হয় অপচয়কারী (traffic-এর নিম্নতম সময়ের জন্য over-provisioned) নয়তো overloaded (traffic-এর শীর্ষ সময়ের জন্য under-provisioned) — বাস্তব traffic কখনো সমতল নয়।
- **এটি সুস্থ কিনা জানার কোনো উপায় নেই।** সংখ্যা ছাড়া উপরের কোনোটিই পরিচালনা করা যায় না: queue কি জমে যাচ্ছে, latency কি ব্যবহারকারীর সহনীয় সীমা ছাড়িয়ে যাচ্ছে, GPU কি আসলেই bottleneck?

নিচের Sections 2 থেকে 6 এই প্রতিটি ফাঁকের উত্তর একে একে দেয়: overload-এর জন্য bounded queues ও admission control (§2), replica-গুলো জুড়ে load ছড়াতে load balancing (§3), capacity বাড়ানো-কমানোর জন্য autoscaling (§4), সুস্থতার জন্য observability (§5), এবং shared capacity-তে উপরের কয়েকটি *একসাথে* ঘটার ক্ষেত্রে multi-tenancy (§6)।

## 2. Request queues এবং admission control

প্রতিটি serving process-এর একটি batch-এ admit হওয়ার অপেক্ষায় থাকা request-এর একটি queue আছে। সেই queue সম্পর্কে একক সবচেয়ে গুরুত্বপূর্ণ design সিদ্ধান্ত হলো এটি অবশ্যই **bounded** হতে হবে — কোনো সর্বোচ্চ গভীরতায় সীমাবদ্ধ — সীমাহীনভাবে বাড়তে দেওয়ার বদলে। একটি unbounded queue নিরাপদ মনে হয় (কিছুই কখনো reject হয় না), কিন্তু টানা overload-এর অধীনে এটি request reject করার চেয়েও খারাপ কিছু করে: এটি সবগুলো গ্রহণ করে এবং *প্রতিটি* request-কে, আগে আসা request-সহ, একটি ক্রমবর্ধমান backlog-এর পেছনে অপেক্ষা করায়। একটি unbounded queue-এর গভীরে admit হওয়া একটি request-এর queueing latency যথেচ্ছ বড় হতে পারে — একজন ব্যবহারকারী কতক্ষণ অপেক্ষা করতে পারেন তার কোনো ঊর্ধ্বসীমা নেই, এবং শেষ পর্যন্ত যখন response ফিরে আসে তখন যে জিজ্ঞেস করেছিল তার কাছে সেটি অকেজো হয়ে যেতে পারে।

**Load shedding** হলো সমাধান: queue তার সীমায় পৌঁছানোর পর, নতুন request-গুলো গ্রহণ করে অপেক্ষায় ফেলে রাখার বদলে reject করা হয় (বা "fast-failed" — সঙ্গে সঙ্গে একটি error ফেরত দেওয়া হয়)। এটি একটি unbounded queue-এর চেয়ে খারাপ ফলাফল মনে হয় — কিছু request কিছুই পায় না — কিন্তু এটি একটি ইচ্ছাকৃত বিনিময়: load shed করা যেকোনো গৃহীত request-এর *worst-case* latency-কে সীমাবদ্ধ করে, এর মূল্য হলো overload চলাকালীন সবাইকে অনির্দিষ্টকাল অপেক্ষায় রাখার বদলে কিছু request সরাসরি ফিরিয়ে দেওয়া। দ্রুত rejection পাওয়া একটি client অন্য replica-তে retry করতে পারে, back off করতে পারে, বা তার নিজের ব্যবহারকারীকে একটি স্পষ্ট error দেখাতে পারে — সবগুলোই নিঃশব্দে কয়েক মিনিট দেরিতে পৌঁছানো একটি response-এর চেয়ে কঠোরভাবে ভালো বিকল্প। `example.py` §1 হুবহু এই বৈপরীত্য simulate করে: একই bursty arrival process একবার একটি unbounded queue-এর মধ্য দিয়ে এবং একবার load shedding-সহ একটি bounded queue-এর মধ্য দিয়ে চালানো, প্রতিটি ক্ষেত্রে প্রকৃত পরিমাপিত queueing-latency percentiles-সহ।

একটি একক admission নিয়মসহ একটি bounded queue এখনো প্রতিটি request-কে অভিন্নভাবে দেখে, যা নিজেই প্রায়ই ভুল: একটি production system সাধারণত একই capacity-র বিপরীতে একাধিক ধরনের traffic serve করে — interactive chat যার জন্য একজন ব্যবহারকারী সক্রিয়ভাবে অপেক্ষা করছেন, এবং batch বা background jobs (একটি রাত্রিকালীন summarization run, একটি evaluation sweep) যেগুলো কেউ real time-এ দেখছে না। **Priority queues** (বা priority *classes*) প্রতিটি traffic class-কে তার নিজস্ব queue এবং নিজস্ব admission/scheduling priority দিয়ে এটি ঠিক করে, যাতে low-priority batch jobs-এর একটি burst capacity ভরিয়ে ফেলে high-priority interactive class-এর latency SLO-কে অনাহারে রাখতে না পারে — batch class কেবল বেশি অপেক্ষা করে, বা আগে shed হয়, যখন interactive class-এর request-গুলো তার আগে admit হয়। এটি সেই একই ধারণা যা §6 multi-tenant স্তরে আবার দেখে: একটি workload-এর burst-কে অন্যটির নিশ্চয়তা নষ্ট করা থেকে বিচ্ছিন্ন রাখা।

## 3. Replica-গুলো জুড়ে load balancing

Lesson 4-এর serving process-এর একাধিক replica হয়ে গেলে, তাদের সামনে থাকা কিছু একটিকে প্রতিটি আগত request-এর জন্য ঠিক করতে হয় কোন replica সেটি পাবে। তিনটি policy, ক্রমবর্ধমান জটিলতার ক্রমে:

- **Round-robin**: request 1 পাঠাও replica 1-এ, request 2 পাঠাও replica 2-এ, এভাবে চলতে থাকো, ঘুরে আবার শুরুতে ফিরে এসো। Implement করা তুচ্ছ, এবং যুক্তিসঙ্গত যখন প্রতিটি request-এর খরচ মোটামুটি একই — কিন্তু বাস্তব LLM request-গুলো মোটেও তা নয়: এক-বাক্যের একটি উত্তর এবং বহু-পৃষ্ঠার একটি response একটি replica-র capacity বিপুলভাবে ভিন্ন সময়ের জন্য দখল করে, এবং round-robin জানে না কোন replica-গুলো বর্তমানে দীর্ঘ-চলমান request-এ ভারাক্রান্ত আর কোনগুলো প্রায় অলস বসে আছে।
- **Least-outstanding-requests**: প্রতিটি নতুন request-কে সেই replica-তে route করো যার বর্তমানে *সবচেয়ে কম* in-flight request আছে। এটি অসম request খরচের সাথে স্বয়ংক্রিয়ভাবে খাপ খাইয়ে নেয় — কয়েকটি দীর্ঘ generation serve করতে আটকে থাকা একটি replica স্বাভাবিকভাবেই নতুন কাজ পাওয়া বন্ধ করে যতক্ষণ না তার কিছু slot মুক্ত হয়, router-কে কোনো নির্দিষ্ট request কতক্ষণ নেবে সে সম্পর্কে কিছু জানার প্রয়োজন ছাড়াই। `example.py` §2 এই বৈপরীত্য সরাসরি পরিমাপ করে: এলোমেলোভাবে পরিবর্তনশীল output length-সহ request-এর একটি stream একটি ছোট স্থির সংখ্যক replica জুড়ে round-robin বনাম least-outstanding-requests দিয়ে route করা, ফলস্বরূপ per-replica load imbalance পরিমাপ করা, ঘোষণা নয়।
- **KV-cache-aware / prefix-aware routing**: একটি request-কে সেই replica-তে route করো যার *ইতিমধ্যে* একটি আগের request থেকে তার prompt prefix memory-তে cached আছে, যে replica-তে এটি অন্যথায় পৌঁছাত সেখানে একটি অপ্রয়োজনীয় prefill সম্পূর্ণ এড়িয়ে। এটি এমন দুটি ধারণার fleet-scale সাধারণীকরণ যা এই phase ইতিমধ্যে একটি একক server-এর স্কেলে কভার করেছে: [Lesson 4 §6](../04-Serving-Frameworks/README.md#6-sglang-automatic-general-purpose-prefix-sharing)-এর RadixAttention একটি SGLang process-এর memory-র *ভেতরে* cached prefix blocks ভাগ করে, এবং [Lesson 6 §2](../06-Cost-and-Latency-Optimization/README.md#2-prefix-caching-paying-for-a-shared-prompt-once)-এর prefix caching একটি server-এর *ভেতরে* একটি shared prompt-এর prefill খরচ amortize করে। Prefix-aware routing হুবহু একই ধারণা নিয়ে সেটিকে একটি *সম্পূর্ণ fleet* জুড়ে প্রসারিত করে: router নিজেই (আনুমানিকভাবে) track করে কোন replica-গুলো কোন cached prefix ধরে রাখে, এবং একটি prefix ভাগ করা request-গুলোকে সেই replica-র দিকে চালিত করে যে ইতিমধ্যে এর দাম দিয়েছে, প্রতিটি replica-র cache-কে বিচ্ছিন্ন ধরে নিয়ে least-outstanding-requests যেখানে পাঠায় সেখানে আবার prefill খরচ দেওয়ার বদলে।

এই তিনটি policy-র কোনোটিই প্রতিটি পরিস্থিতিতে কঠোরভাবে ভালো নয় — round-robin সবচেয়ে সরল এবং যথেষ্ট ভালো যখন request খরচ সত্যিই মোটামুটি সমান; least-outstanding-requests অসম LLM workload-এর জন্য standard পছন্দ; prefix-aware routing বিশেষভাবে লাভজনক যখন traffic-এর একটি বড় অংশ প্রকৃত prompt prefixes ভাগ করে (দীর্ঘ system prompts, shared retrieved documents), এবং সঠিকভাবে করতে কিছু routing জটিলতার খরচ লাগে।

## 4. Autoscaling

একটি স্থির সংখ্যক replica হলো একটি স্থির capacity ঊর্ধ্বসীমা, *কোনো একটি* traffic স্তরের জন্য মাপা — শান্ত সময়ে খুব বেশি replica GPU খরচ অপচয় করে, শীর্ষ সময়ে খুব কম মানে §2-এর queues ভরে যায় এবং request shed হতে শুরু করে। **Autoscaling** একটি হাতে-বাছা ধ্রুবকের বদলে পর্যবেক্ষিত load-এর ভিত্তিতে স্বয়ংক্রিয়ভাবে replica যোগ ও অপসারণ করে, সেই একই signals দ্বারা চালিত যা §5 নির্ভুলভাবে সংজ্ঞায়িত করে: queue depth (admission queue এই মুহূর্তে কতটা জমে আছে), একটি SLO threshold অতিক্রম করা p99 latency (গৃহীত request-গুলো কি এটি অনুভব করতে শুরু করেছে), এবং GPU utilization (বিদ্যমান capacity আসলেই ব্যস্ত নাকি অলস বসে আছে)।

LLM serving-এর একটি autoscaling জটিলতা আছে যা একটি সাধারণ stateless web service-এর নেই: **cold start ব্যয়বহুল**। একটি stateless web replica scale up করা সাধারণত মানে কয়েক সেকেন্ডে একটি হালকা process শুরু করা। একটি LLM-serving replica scale up করা মানে সেই replica একটি request-ও serve করার আগে disk বা network storage থেকে GPU memory-তে একটি model-এর weights — প্রায়ই দশ দশ gigabyte — load করা, যা একটি সাধারণ service-এর cold start-এর চেয়ে উল্লেখযোগ্যভাবে বেশি সময় নিতে পারে। Autoscaling-কে *কখন* প্রতিক্রিয়া দেখাতে হবে তার উপর এর সরাসরি প্রভাব আছে: যেহেতু একটি নতুন replica তার (ধীর) cold start শেষ না হওয়া পর্যন্ত আসলে উপযোগী নয়, autoscaler-কে বাড়তে থাকা load-এ queue আসলে উপচে পড়ার অনেক *আগেই* প্রতিক্রিয়া দেখাতে হবে — queue-depth trend বা প্রাথমিক latency বৃদ্ধির মতো একটি leading indicator-এর উপর scale করে, queue ইতিমধ্যে ভরে যাওয়ার উপর নয় — নইলে নতুন capacity সেই burst-কে সাহায্য করতে খুব দেরিতে পৌঁছাবে যা এটিকে ট্রিগার করেছিল।

## 5. Observability: standard metric vocabulary

§2-4-এর সবকিছুই পদক্ষেপ নেওয়ার মতো সংখ্যা ছাড়া অপরিচালনাযোগ্য। এই section নির্ভুলভাবে সংজ্ঞায়িত করে একটি production LLM-serving system যে standard metrics report করে — কিছু ইতিমধ্যে উপস্থাপিত, বাকিগুলো vocabulary সম্পূর্ণ করে।

**TTFT (Time to First Token)** এবং **ITL (Inter-Token Latency)** ইতিমধ্যে [Lesson 3 §7](../03-KV-Cache-and-Speculative-Decoding/README.md#7-ttft-and-itl-the-two-per-request-latency-metrics)-এ সংজ্ঞায়িত হয়েছে: TTFT হলো request আগমন থেকে প্রথম output token পর্যন্ত latency (prefill দ্বারা আধিপত্যকৃত, যোগ queueing সময়), এবং ITL হলো প্রতিটি পরবর্তী output token-জোড়ার মধ্যকার latency (একটি decode ধাপের খরচ)। এই lesson যোগ করে:

- **TPOT (Time Per Output Token)**: একটি সম্পূর্ণ request জুড়ে *গড়* per-token decode latency, একটি request-এর মোট latency থেকে সরাসরি গণনা করা:

  ```
  TPOT = (total_latency - TTFT) / (num_output_tokens - 1)
  ```

  TPOT এবং ITL *একই অন্তর্নিহিত per-step খরচ* পরিমাপ করে — একটি decode ধাপের memory-bandwidth-bound খরচ — কিন্তু ভিন্ন granularity-তে: ITL প্রতিটি আলাদা ধাপের জন্য report হয় (বা ধাপগুলো জুড়ে একটি distribution হিসেবে), যখন TPOT হলো একটি request-এর পুরো decode phase জুড়ে গড় করা একটি একক সংখ্যা। কিছু literature ও কিছু serving framework "TPOT" এবং "average ITL" পরস্পর বিনিময়যোগ্যভাবে ব্যবহার করে; এটি কোনো ভুল নয়, এটি একইভাবে গণনা করা একই রাশি, কেবল দুটি ভিন্ন নামে। `example.py` §3 simulated per-token completion timestamps থেকে দুটোই সরাসরি গণনা করে, যাতে সম্পর্কটি একটি সংজ্ঞাগত footnote হিসেবে রেখে না দিয়ে প্রকৃত সংখ্যায় দৃশ্যমান হয়।

- **Throughput** (tokens/sec): *per-request* স্তরে, throughput হলো সেই একটি request-এর জন্য সহজভাবে `num_output_tokens / total_latency`। Capacity planning-এর জন্য অনেক বেশি গুরুত্বপূর্ণ হলো *aggregate* (fleet-level) throughput: এই মুহূর্তে একসাথে serve হওয়া প্রতিটি request জুড়ে উৎপাদিত tokens/sec-এর যোগফল, যা সেই সংখ্যা যেটি আসলে উত্তর দেয় "এই deployment কতটা traffic সামলাতে পারে।" একটি server-এর মাঝারি মানের per-request throughput থাকতে পারে (প্রতিটি আলাদা request একা serve করার চেয়ে দ্রুত মনে হয় না) অথচ চমৎকার aggregate throughput থাকতে পারে, কারণ এটি একসাথে এরকম অনেক request serve করছে — এটিই ঠিক Lesson 4-এর কভার করা batching-এর সুফল, একটি সুবিধা হিসেবে ঘোষণার বদলে একটি সংখ্যা হিসেবে পরিমাপিত।

- **Concurrency**: একটি server একসাথে কতগুলো request/sequence serve করছে — in-flight sequence-এর জীবন্ত গণনা যা continuous batching ([Lesson 4 §4](../04-Serving-Frameworks/README.md#4-hugging-face-tgi-continuous-in-flight-batching)) প্রতিটি scheduling tick-এ তার উপলব্ধ slot-গুলোতে dynamically ভরছে। Concurrency হলো সেই input যা aggregate throughput তৈরি করে: বেশি concurrent sequence সাধারণত মানে উচ্চতর aggregate throughput, যতক্ষণ না hardware-এর memory-bandwidth (বা compute) ঊর্ধ্বসীমায় পৌঁছানো হয়।

- **GPU utilization**: GPU-র compute units আসলে কাজ চালাতে ব্যস্ত থাকার সময়ের ভগ্নাংশ। এটি সেই metric যা সবচেয়ে বেশি *ভুলভাবে পড়া* হয়: একটি উচ্চ utilization সংখ্যা শুনতে মনে হয় "GPU-ই bottleneck, আরও GPU যোগ করো" বা "সবকিছু দক্ষতার সাথে চলছে," কিন্তু [Lesson 1 §6](../01-GPU-and-Hardware-Fundamentals/README.md#6-the-payoff-why-prefill-is-compute-bound-and-decode-is-memory-bound) ইতিমধ্যে প্রতিষ্ঠা করেছে যে decode হলো *memory-bandwidth*-bound, compute-bound নয় — একটি GPU উচ্চ "utilization" দেখাতে পারে (এর compute units প্রযুক্তিগতভাবে instruction issue করছে, অথবা profiler-এর "busy" ধারণা একটি memory-bound kernel-এর জন্য অপেক্ষার সময়কেও গোনে) যখন প্রকৃত bottleneck হলো bandwidth, FLOPs নয়। GPU utilization-কে সবসময় Lesson 1-এর compute-bound/memory-bound পার্থক্যের পাশাপাশি পড়তে হবে, bottleneck আসলে কোথায় তার একটি স্বতন্ত্র রায় হিসেবে কখনো নয়।

একসাথে, TTFT/ITL/TPOT/throughput/concurrency/GPU-utilization হলো ঠিক সেই সংখ্যাগুলো যেগুলো *দিয়ে* [Lesson 6](../06-Cost-and-Latency-Optimization/README.md)-এর batching ও prefix-caching trade-off-গুলোর বিনিময় হয় — ওই lesson trade-off-এর আকৃতি বর্ণনা করে (বড় batch throughput বাড়ায় এবং latency বাড়ায়); এই lesson-এর vocabulary হলো একটি প্রকৃত চলমান system-এ সেই trade-off কীভাবে পরিমাপ ও report করা হয়।

## 6. Multi-tenancy

Production capacity কদাচিৎ একটি একক workload-এর জন্য নিবেদিত থাকে — একই GPU fleet প্রায়ই একসাথে একাধিক model, বা একাধিক customer, বা একাধিক অভ্যন্তরীণ team-এর workload serve করে। এটি tenant স্তরে হুবহু সেই সমস্যা ফিরিয়ে আনে যা §2-এর priority classes traffic-class স্তরে সমাধান করেছিল: **noisy-neighbor সমস্যা**, যেখানে একটি tenant-এর traffic burst একই অন্তর্নিহিত capacity ভাগ করা প্রতিটি *অন্য* tenant-এর latency নষ্ট করে, যদিও সেই অন্য tenant ভিন্ন কিছুই করেনি।

সাধারণ প্রশমন হলো **per-tenant SLOs, rate limits, এবং quotas**: shared capacity-র কতটা (requests/sec, concurrent sequences, tokens/sec) কোনো একটি tenant ব্যবহার করতে পারবে তা সীমাবদ্ধ করা, যাতে tenant A-র একটি burst tenant B-র latency নিশ্চয়তাকে অনাহারে রাখার আগেই সীমাবদ্ধ হয় — §2-এর সেই একই priority-queue ধারণা, কেবল traffic class-এর বদলে tenant অনুযায়ী বিভক্ত।

তবে tenant-রা আসলে কতটা বিচ্ছিন্ন, তা একটি সমাধান-হয়ে-যাওয়া সমস্যা নয় বরং একটি প্রকৃত, অমীমাংসিত trade-off। কিছু serving stack tenant-দের সম্পূর্ণভাবে process বা GPU স্তরে বিচ্ছিন্ন করে — tenant A-র request কখনো tenant B-র সাথে একটি batch, একটি KV cache, এমনকি একটি GPU-ও ভাগ করে না — যা শক্তিশালী isolation দেয় (tenant A যা-ই করুক তা কখনো tenant B-কে ধীর করতে পারে না) utilization-এর মূল্যে (প্রতিটি tenant-এর নিবেদিত capacity অলস বসে থাকে যখনই সেই tenant-এর নিজের traffic কম, ঠিক সেই static-allocation অপচয় যা এই পুরো lesson এড়াতে চাইছে)। অন্যরা tenant-দের জুড়ে একটি একক continuous-batching process ভাগ করে, সবার request একই batch ও একই GPU memory-তে ভরে — অনেক ভালো utilization (কারো অলস capacity অপচয় হয় না), কিন্তু বস্তুগতভাবে কঠিনতর isolation (একটি tenant-এর burst অন্য সবার মতোই একই batch slots ও একই memory bandwidth-এর জন্য প্রতিযোগিতা করে, এবং উপরের priority/quota যন্ত্রপাতি কেবল ক্ষতি সীমাবদ্ধ করে, দূর করে না)। বাস্তব production system-গুলো এই বর্ণালীতে ইচ্ছাকৃতভাবে একটি বিন্দু বেছে নেয়, এবং একই deployment-এর ভিন্ন tenant বা ভিন্ন pricing tier প্রায়ই একই সাথে এর ভিন্ন ভিন্ন বিন্দুতে বসে।

## 7. Request/response API surface

§1-6-এর সবকিছু একটি client আসলে যে interface call করে তার *পেছনে* থাকে, এবং সেই interface-এর নিজস্ব design-এর নিজেরই প্রকৃত cost ও latency পরিণতি আছে, কেবল একটি syntactic পছন্দ নয়। দুটি সিদ্ধান্ত প্রধান:

- **Streaming বনাম buffered responses।** একটি LLM তার output এক সময়ে একটি token করে তৈরি করে (এই পুরো phase-এর decode loop), এবং একটি naive API যা ফেরত দেওয়ার আগে *সম্পূর্ণ* response buffer করে, সেটি client-কে পুরো generation-এর জন্য অপেক্ষা করতে বাধ্য করে — client-এর দৃষ্টিকোণ থেকে TTFT ও মোট latency একই সংখ্যায় মিশে যায়, §5-এর অন্তর্নিহিত TTFT আসলে যত ভালোই হোক না কেন। **Streaming** (decode তৈরি করামাত্র প্রতিটি token, বা token-এর ছোট chunk, client-কে ফেরত দেওয়া — সাধারণত Server-Sent Events বা একটি chunked HTTP response-এর মাধ্যমে) হলো সেটিই যা TTFT-কে আদৌ একটি *দৃশ্যমান*, ব্যবহারকারী-মুখী সংখ্যা বানায়: একটি streamed response render করা client প্রথম token প্রস্তুত হওয়ামাত্র দেখাতে পারে, পুরো request-এর মোট latency জুড়ে একটি ফাঁকা screen-এর দিকে তাকিয়ে থাকার বদলে। এই কারণেই কার্যত প্রতিটি production LLM API streaming-কে একটি first-class mode হিসেবে সমর্থন করে, পরে-ভাবা কিছু হিসেবে নয়।
- **একটি shared request/response schema।** প্রথম দিকের LLM-serving API-গুলো প্রত্যেকে "prompt in, tokens out"-এর জন্য নিজস্ব JSON আকৃতি উদ্ভাবন করেছিল। বাস্তবে, OpenAI Chat Completions API-এর request/response schema (role-tagged messages-এর একটি তালিকা in, একটি message সাথে token-usage হিসাব out, উপরে বর্ণিত streaming mode toggle করতে একটি `stream` flag-সহ) হয়ে উঠেছে de facto standard যার জন্য বেশিরভাগ self-hosted serving framework — [Lesson 4](../04-Serving-Frameworks/README.md)-এর vLLM, TGI ও SGLang-সহ — এখন একটি OpenAI-*compatible* endpoint implement করে, কেবল যাতে ওই schema-র বিপরীতে তৈরি বিদ্যমান client tooling একটি self-hosted model-এর বিপরীতে অপরিবর্তিত অবস্থায় কাজ করে। এটি একটি প্রচলন, §1-6-এর কোনো যন্ত্রপাতির প্রযুক্তিগত প্রয়োজনীয়তা নয়, কিন্তু বাস্তবে এটি গুরুত্বপূর্ণ: এই কারণেই "এই endpoint-এর পেছনে কোন model আছে তা বদলাও" সাধারণত একটি client rewrite-এর বদলে এক-লাইনের config পরিবর্তন।

কোনো সিদ্ধান্তই request কীভাবে queue, balance, scale বা observe করা হয় সে সম্পর্কে কিছু বদলায় না (§2-6 সম্পূর্ণভাবে এই interface-এর নিচে বসে) — কিন্তু দুটোই সরাসরি গড়ে দেয় একজন *client* কী অভিজ্ঞতা পায়, যা শেষ পর্যন্ত §5-এর প্রতিটি metric-এর মূল উদ্দেশ্য।

## 8. Recap: সবকিছু কীভাবে একত্রিত হয়

একসাথে রাখলে, §2-6 একটি system গঠন করে: একটি bounded, priority-aware queue (§2) এমন একটি capacity পর্যন্ত request admit করে যা autoscaling (§4) load-এর প্রতিক্রিয়ায় সমন্বয় করে; একটি load balancer (§3) admit হওয়া request-গুলো বর্তমানে বিদ্যমান replica-গুলো জুড়ে ছড়িয়ে দেয়, prefix-aware routing যোগ হওয়ার সাথে সাথে ক্রমশ আরও বুদ্ধিমত্তার সাথে; observability (§5) হলো সেই instrumentation যা এই system-এর প্রতিটি অন্য অংশকে, এবং এটি চালানো মানুষদের, বলে দেয় এটি আসলে কাজ করছে কিনা; multi-tenancy (§6) হলো যা ঘটে যখন কয়েকটি traffic class বা কয়েকজন customer একই সাথে এই একই যন্ত্রপাতির উপর নির্ভর করে, isolation ও utilization বিপরীত দিকে টানে; এবং §7-এর API surface হলো সেই interface যার মাধ্যমে একটি client আসলে উপরের সবকিছু অভিজ্ঞতা করে। একটি বাস্তব deployment-এ এই অংশগুলোর কোনোটিই ঐচ্ছিক নয় — admission control ছাড়া একটি queue কেবল একটি outage বিলম্বিত করে, load balancing ছাড়া একটি fleet replica অপচয় করে, autoscaling ছাড়া replica-গুলো অর্থ অপচয় করে বা request ফেলে দেয়, এবং observability ছাড়া উপরের যেকোনোটি অপরিচালনাযোগ্য।

[Lesson 11 (Frontier Inference Systems)](../11-Frontier-Inference-Systems/README.md) ঠিক সেখান থেকে শুরু করে যেখানে §3-এর load-balancing/routing ধারণাগুলো থেমেছে এবং সেগুলোকে আরও এগিয়ে নেয়: *prefill* ও *decode* phase-গুলোকে আলাদা, ভিন্নভাবে-provisioned hardware pool-এ disaggregate করা (যেহেতু [Lesson 1 §6](../01-GPU-and-Hardware-Fundamentals/README.md#6-the-payoff-why-prefill-is-compute-bound-and-decode-is-memory-bound) ইতিমধ্যে প্রতিষ্ঠা করেছে যে তাদের বিপরীত compute/memory profile আছে, তাই তাদের আদৌ একই replica ভাগ করতে হবে না), এবং ভিন্ন ভিন্ন hardware প্রজন্ম জুড়ে cache-topology-aware routing — এই lesson যে fleet-scale routing সমস্যা উপস্থাপন করে সেই একই সমস্যা, এমন এক স্তরের জটিলতায় যা এখন পর্যন্ত কেবল frontier serving system-গুলোকেই তৈরি করতে হয়েছে।

## ভিডিও স্ক্রিপ্ট আউটলাইন

1. প্রেরণা — Lesson 4-এর একটি একক serving process একটি production system নয়; চারটি ফাঁক: overload, load ছড়ানো, capacity scale করা, এবং এটি সুস্থ কিনা জানা
2. Bounded queues ও load shedding: কেন unbounded queueing latency-কে সীমাহীনভাবে বাড়তে দেয়, এবং কীভাবে shedding কয়েকটি rejection-এর বিনিময়ে একটি সীমাবদ্ধ worst case দেয়
3. Priority classes: একটি traffic class-এর burst-কে অন্যটির SLO অনাহারে রাখা থেকে বিরত রাখা
4. `example.py` §1-এর walkthrough — একটি bursty arrival process-এর অধীনে unbounded বনাম bounded-queue-with-shedding, প্রকৃত p50/p99 queueing latency ও reject সংখ্যা
5. Load balancing: round-robin বনাম least-outstanding-requests বনাম prefix-aware routing, এবং কেন অসম request খরচ প্রথমটিকে LLM traffic-এর জন্য খারাপ মানানসই করে
6. `example.py` §2-এর walkthrough — পরিবর্তনশীল service times-এর অধীনে round-robin বনাম least-outstanding-requests, replica-গুলো জুড়ে পরিমাপিত load imbalance
7. বাস্তব signal-এর উপর autoscaling, এবং LLM-নির্দিষ্ট cold-start সমস্যা যা autoscaler-দের আগেভাগে প্রতিক্রিয়া দেখাতে বাধ্য করে
8. সম্পূর্ণ metric vocabulary: TTFT, ITL, TPOT, throughput (per-request বনাম aggregate), concurrency, GPU utilization — এবং utilization/memory-bound ভুল-পড়ার ফাঁদ
9. `example.py` §3-এর walkthrough — simulated per-token timestamps থেকে সরাসরি গণনা করা TTFT/TPOT/throughput
10. Multi-tenancy, noisy-neighbor সমস্যা, এবং per-tenant GPU ও একটি shared continuous-batching process-এর মধ্যে প্রকৃত isolation-বনাম-utilization trade-off
11. API surface নিজেই: কেন streaming TTFT-কে একটি প্রকৃত, ব্যবহারকারী-দৃশ্যমান সংখ্যা বানায়, এবং কীভাবে OpenAI-compatible schema বেশিরভাগ self-hosted server-এর implement করা de facto interface হয়ে উঠল
12. সম্পূর্ণ system-এর recap, এবং Lesson 11-এর disaggregated prefill/decode pools ও cache-topology-aware routing-এর দিকে ইঙ্গিত
