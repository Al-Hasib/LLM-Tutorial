# Standard Benchmarks

**Phase:** [Evaluation of LLMs](../README.md) · **Topic folder:** `02-Standard-Benchmarks`

## Why this matters

[Lesson 1](../01-Evaluation-Metrics/README.md) covered *general-purpose* metrics you can apply to any (candidate, reference) pair. This lesson covers the *specific, standardized datasets* that the field actually runs those (and other) metrics on to compare models against each other — the numbers you see in every model release's "results" table (MMLU score, HellaSwag accuracy, GSM8K accuracy, HumanEval pass@1). These benchmarks matter for a very concrete reason: they are the closest thing the field has to a controlled experiment for "is this model actually better," and understanding *exactly* how they're scored under the hood is what separates reading a leaderboard number correctly from misreading it. This lesson also sets up [Lesson 3: LLM-as-a-Judge](../03-LLM-as-a-Judge/README.md) directly — benchmarks like these work only because they have a single unambiguous correct answer to check against; open-ended generation (write me an essay, have a conversation) has no such gold answer, which is exactly the gap LLM-as-a-Judge is built to fill.

## What this lesson covers

- MMLU: broad multiple-choice knowledge across 57 subjects

- The pass@k unbiased estimator formula, derived and sanity-checked

## 1. MMLU: broad multiple-choice knowledge

MMLU (**Massive Multitask Language Understanding**, Hendrycks et al., 2021) is a multiple-choice benchmark spanning 57 subjects — elementary math, US history, computer science, law, medicine, professional accounting, and more — each question presented with 4 answer options (A/B/C/D). It's meant to probe broad factual and reasoning knowledge acquired during pretraining, not any one narrow skill. Because it spans so many disconnected subjects, a single MMLU accuracy number is often treated as a rough proxy for a model's general knowledge breadth.

## 2. HellaSwag: adversarial commonsense completion

HellaSwag (Zellers et al., 2019) presents a sentence or short scenario and 4 possible endings; the model must pick the ending a human would judge as the natural continuation. What makes it hard is *how the wrong endings were built*: they were generated by a language model and then filtered by **Adversarial Filtering** to keep only the wrong endings that *another* strong language model still scored as plausible (i.e., the wrong options are specifically chosen to fool models, while remaining obviously wrong to a human). This adversarial construction is what makes HellaSwag meaningfully harder than a benchmark with randomly-written wrong answers — it directly targets the failure modes of language-model-based distractor generation.

## 3. GSM8K: grade-school math word problems

GSM8K (Cobbe et al., 2021) is a set of ~8,500 grade-school-level math word problems requiring multi-step arithmetic reasoning (e.g., "Natalia sold clips to 48 of her friends in April... how many clips did she sell altogether?"). Unlike MMLU/HellaSwag, it is not multiple choice — the model must produce a free-form numeric final answer, which is extracted from the model's output text and checked for exact match against the ground-truth number. Because the problems require several sequential reasoning steps, GSM8K accuracy is extremely sensitive to *how* the model is prompted: with a direct "give me the number" prompt, models historically did poorly; with **chain-of-thought prompting** (asked to show intermediate reasoning steps before the final number — see [Phase 07 Lesson 2](../../Phase-07-Prompt-Engineering-and-In-Context-Learning/02-Chain-of-Thought-and-Reasoning-Prompts/README.md)), accuracy jumps dramatically. GSM8K is the standard benchmark used to demonstrate that chain-of-thought prompting helps.

## 4. HumanEval: code generation, graded by execution

HumanEval (Chen et al., 2021, the Codex paper) gives the model a function signature plus a docstring describing the desired behavior, and asks it to complete the function body. Crucially, grading is **not** text-overlap-based at all — a generated solution is graded by actually *running* it against a held-out suite of unit tests. This sidesteps every weakness from Lesson 1 entirely: there is no "surface overlap vs. paraphrase" problem, because two completely different-looking implementations that both pass all the tests are both scored as fully correct.

### pass@k

Because sampling from a language model is stochastic, HumanEval doesn't just check "was the one greedy completion correct" — it draws `n` samples per problem and asks: if you were allowed to submit `k` of those `n` samples and only needed *one* to pass, what's the probability of success? Naively estimating this by literally drawing many random subsets of size `k` is wasteful and noisy. Chen et al. (2021) derive a low-variance, unbiased **closed-form estimator** instead: given `n` total samples drawn per problem and `c` of them that passed all unit tests,

```
pass@k = 1 - C(n - c, k) / C(n, k)
```

where `C(a, b)` is "a choose b". Read the formula directly: `C(n-c, k) / C(n, k)` is the probability that a *randomly chosen* subset of `k` samples (out of the `n` drawn) contains **zero** correct ones (you're choosing all `k` from only the `n-c` incorrect samples), so `1` minus that is the probability the subset contains **at least one** correct sample — exactly what "pass@k" means. This is evaluated per problem and then averaged across the benchmark's problems to get the final pass@k score.

## 5. How multiple-choice benchmarks are actually scored

A common misconception: that a model is graded on MMLU/HellaSwag by literally generating text and checking whether it outputs the letter "A", "B", "C", or "D". That is **not** how the standard evaluation harnesses (e.g., EleutherAI's `lm-evaluation-harness`, used to produce most published numbers) actually do it. Instead:

1. Format the question once per candidate answer, as a single continuous string: `"{question}\n{answer_option_text}"` (some harnesses instead format it as `"{question}\nAnswer: {letter}"` — but even then, they score the *letter token's* log-probability, not the model's free-text output).
2. Run the model once per candidate, in **teacher-forcing** mode, and sum the log-probabilities the model assigns to the tokens of that specific answer text, conditioned on the shared question prefix.
3. Pick whichever candidate has the **highest total (or length-normalized) log-probability**.

This log-likelihood-comparison approach is preferred over "ask the model to emit a letter and parse its output" for a very practical reason: it is robust to a model's formatting quirks, refusal behavior, and verbosity. A model might produce a rambling response that never cleanly outputs a bare letter, or might have a token-level bias toward certain letters that has nothing to do with which answer it actually finds most probable — comparing full-answer log-probabilities directly measures what the question was actually designed to test (which completion does the model's own distribution favor), independent of surface output formatting. `example.py` implements exactly this scoring method against a real (if tiny) trained model.
